# Контракт транспортов генерации Codex

2026-09-18 пользователь выбрал добавить app-server рядом с exec и сравнить нагрузку.
Оба реализованы; по решению пользователя основной режим — app-server. Exec выключен по умолчанию и доступен только при явном выборе, без автоматического fallback. Каноническая эксплуатация и расчёт:
[docs/codex-transports.md](../../../../docs/codex-transports.md).

## Поведение

- Экран Codex использует общую с Kie двухколоночную компоновку: форма,
  стоимость и запуск слева; состояние текущего задания, просмотр результата,
  скачивание PNG и параметры справа. На узком экране колонки располагаются
  последовательно. Пустое превью скрывается после успеха; при новом задании
  старый результат скрывается. Неопределённый исход сохраняет блокировку
  повторной отправки и возможность проверить статус. Настройки модели,
  усилия, скорости и типа результата остаются в меню провайдера.
- Одинаковая компоновка не добавляет Codex управление очередью Kie: пауза,
  очистка очереди и пользовательский лимит параллельности к Codex не относятся.
  Исходные PNG/JPEG/WebP загружаются в аккаунт и передаются worker как
  референсы; app-server v2 получает их как `UserInput { type: "image", url }`,
  aspect ratio передаётся в промпт генерации.

- Серверный выбор `MEDIA_CODEX_TRANSPORT=exec|app-server`, без изменения формы
  пользовательской генерации и без автоматического fallback/replay.
- Каталог моделей — отдельный read-only контракт worker `GET /models`:
  активный app-server вызывает `model/list` с пагинацией и `includeHidden:false`,
  нормализует ID, названия, уровни рассуждения и входные модальности, кеширует
  ответ на 60 секунд. В режиме `exec` тот же аккаунт опрашивается отдельным
  app-server только для каталога; транспорт генерации не меняется. Веб-сервис
  отдаёт авторизованным пользователям `GET /api/codex/models` из этого worker,
  добавляя прежние `uiDefaults`. На ошибке worker возвращается 503 без старого
  снимка. Клиент, биллинг и worker проверяют запрос по живому каталогу;
  отсутствие опубликованной цены по-прежнему запрещает резерв и запуск.
- Exec запускает отдельный процесс на запрос. App-server сохраняет stdio-процесс,
  создаёт отдельный ephemeral thread/turn на запрос и маршрутизирует события
  по threadId/turnId. Завершённые threads отписываются, группа процессов
  останавливается вместе с worker. Несколько серверных аккаунтов не реализованы.
- Общий контракт результата: output, imageBase64 при image, нормализованный usage.
  В app-server usage берётся из `thread/tokenUsage/updated.tokenUsage.total`:
  каждый thread содержит ровно один turn, включая его внутренние обращения к модели.
- Неопределённый исход транспорта/таймаута сохраняет резерв через state unknown.
  Подтверждённый failed/interrupted turn возвращает резерв. Повтор идемпотентного
  HTTP-запроса не создаёт повторную генерацию.
- Общий `submission-control` разрешает повтор только для HTTP 429 от worker с
  явным `accepted: false`. До срока `retryAfterAt` задача остаётся `queued` с
  тем же резервом; после перезапуска безопасное ожидание восстанавливается.
  HTTP 429 без доказательства отказа и любой потерянный ответ остаются `unknown`.
- Настройки read-only/never, отключённые shell/browser/apps/hooks и контроль
  trusted thread PNG обязательны. В app-server 0.155.0 PNG обычно приходит inline
  в `item/completed` у элемента `imageGeneration`; адаптер валидирует результат и
  сохраняет trusted thread directory как резерв. Наличие пользовательского
  config.toml — явный отказ, поскольку флаг ignore-user-config отсутствует.
- Текстовые запросы (включая отсутствие kind) с 2026-10-02 используют встроенный
  `web_search=live` в exec и app-server. Общая политика `codexWebSearch` в
  `src/services/codex-request.js` разрешает поиск и открытие публичных URL только
  для текста; image сохраняет disabled. Промпт больше не запрещает все инструменты,
  учитывает явный запрет пользователя на поиск, отделяет содержимое страниц от
  инструкций и требует ссылок на использованные источники. Ограничения сервиса
  нельзя приписывать пользователю. Shell, server files, browser/apps/hooks,
  read-only/never и фильтр окружения сохраняются. Публичный request/response
  контракт, цены и правила повтора не меняются. Проверки политики:
  `test/codex-web-search.test.js`, `test/codex-app-server.test.js`.
- Чтение URL из запроса «изучи/открой/прочитай» дополнено серверным JavaScript
  snapshot: `codex-web-context.js` готовит общий prompt для exec/app-server,
  `codex-page-reader.js` владеет временным профилем Chromium и уничтожает его
  после чтения. До двух браузеров одновременно на worker; ожидание входит в
  лимит времени. До двух HTTPS URL, до 25 секунд на страницу, 100 GET ресурсов,
  4 MiB на ресурс и 12 MiB суммарно. Только порт 443; запрет пользователя на
  просмотр и image отключают чтение. POST, cookies, секретные заголовки и
  авторизованные профили не передаются. Chromium имеет недоступный proxy;
  Fetch interception загружает ресурсы через общий `public-web-fetch.js` с
  проверкой всех DNS адресов и закреплением IP. Каждый redirect вновь проходит
  проверку. Модель получает URL, статус, заголовок, видимый текст и ссылки как
  недоверенные данные; должна отличать наблюдение от непроверенных сценариев.
  Ошибка snapshot не повторяет генерацию и оставляет встроенный поиск доступным.
  Публичные API, биллинг и итоговый контракт результата не меняются.
- Часовой кеш worker одинаков для обоих режимов. Нельзя обещать немедленное
  освобождение памяти app-server после unsubscribe; длительная нагрузка не проверена.

## Карта и доказательства

Сборка 2026-10-01: `src/server/codex-module.js` связывает worker-client,
records, pricing/conversion и content. Пользовательские маршруты используют
provider facade, административные — admin facade. Worker не зависит от
пользовательской БД, кредитов или ContentService. Продуктовая оркестрация
`codex-billing.js` работает с переданными интерфейсами; атомарность резерва,
записи, settlement и журнала принадлежит Generations/CodexRecords.
Внешние HTTP API, requestId, цены, tenant scope и правила повтора сохранены.
Проверки границ: `test/module-boundaries.test.js`; транспорт:
`test/codex-worker-client.test.js`; собранный сценарий с PostgreSQL:
`test/codex.test.js`. Остальные провайдеры и Vue рефакторятся по
`docs/modularity-improvement-plan.md` и не объявляются завершёнными.

Ошибки изображений (2026-10-01): `codex-errors.imageGenerationError` читает
только явные `failure`, `error` и ограниченный текстовый `result`; бинарный
результат и поля запроса не копируются. App-server сохраняет ошибку элемента
до `turn/completed`, чтобы учесть итоговый `turn.error` или неповторяемое
уведомление `error`. При отсутствии причины возвращается явное пояснение,
а не предположение о модерации/лимите. Известные коды модерации и лимита
получают понятную подпись с сохранением исходных безопасных деталей.
История показывает это владельцу; старый общий текст отображается через RU/EN
словарь без изменения записей БД. Проверки: `test/codex-errors.test.js`,
`test/codex-app-server.test.js`. Транспорт без завершения turn по-прежнему
попадает в `unknown`; автоматические повторы и расчёты кредитов не меняются.

- `src/services/codex-worker.js`: выбор транспорта, дедупликация, кеш и shutdown.
- `src/services/codex-exec.js`: прежний exec-путь; `codex-runtime.js`: фильтр окружения.
- `src/services/codex-app-server.js`: JSON-RPC, threads/turns, ошибки, PNG и usage.
- `src/services/codex-request.js`: единые промпты и перечни feature-политик.
- `src/services/codex-billing.js`: unknown сохраняет резерв для обоих транспортов.
- `test/codex-app-server.test.js`, `test/codex.test.js`: мультиплексирование,
  события до ответа RPC, PNG, shutdown, отказ конфигурации и учёт unknown.
- `scripts/benchmark-codex-transports.cjs`: воспроизводимый ограниченный A/B.
- Живое доказательство вне Git:
  `artifacts/load-tests/transport-2026-09-18T16-05-50-682Z/events.jsonl`.
  12/12 успехов, GPT-5.5/medium/Fast; account budget пользователя исчерпан этим
  тестом (6 текстов + 6 изображений). Новые живые запросы требуют нового бюджета.

Вывод пилота: app-server использовал примерно вдвое меньше локального CPU,
но сообщил больше CLI-токенов; ускорение пары PNG около 4%, пары текстов около 40%
по throughput одной волны. Это не денежная оценка и не мощность Bothost.
Сквозной и длительный [план нагрузки](codex-load-testing.md) остаётся невыполненным.

## Пул 2 × 128 (2026-09-18)

По запросу пользователя worker использует два независимых app-server с одним
CODEX_HOME/аккаунтом, по 128 активных заданий на процесс. FIFO-очередь сверх 256,
выбор наименее занятого процесса, без повторов и fallback в exec. Лимит
распространяется на текст и изображения суммарно. Приватный health показывает
пул и его очередь; настройки описаны в docs/codex-transports.md.

Реальная проверка 2 × 128: 256 отправок, 2 failed, 254 unknown, 0 PNG; общий
обрыв через 15–17 секунд. Пул включён, но эта нагрузка не подтверждена.
Подробности и evidence: docs/codex-capacity.md. Не повторять unknown автоматически.

## Атомарная публикация результатов — 2026-09-30

`src/services/codex-worker.js` владеет JSON/PNG результатами в resultDirectory.
GET /jobs/:id сообщает success/failed только после атомарной записи итогового
JSON; PNG записывается раньше success. До сохранения память остаётся running,
поэтому потребитель не подтверждает и не оплачивает ещё несохранённый результат.
После рестарта результат читается с диска без повторного run. Отсутствующий
job возвращает 404: billing сохраняет unknown и резерв, не отправляет платный
запрос повторно; диагностика получает CODEX_HTTP_404. Проверки:
`test/codex.test.js` (durable success, restart, 105 jobs, unknown reservations).

Уточнение 2026-10-02: первый 404 чтения статуса сохраняет в CodexRecords
`state=unknown`, `errorCode=CODEX_WORKER_JOB_MISSING`. Worker добавляет во все
JSON-ответы приватный заголовок X-Codex-Worker-Instance (UUID жизни процесса).
CodexRecords атомарно объединяет missingWorkerInstanceIds под блокировкой,
сохраняя последние 8 UUID. Billing сверяет текущий UUID через health; для уже
известного отсутствия возвращает запись без GET задания и новой ревизии,
включая recover после перезапуска media. Другой или перезапущенный worker
опрашивается снова и может вернуть сохранённый результат; успех очищает маркер.
Старый worker без UUID не даёт оснований прекращать уточнение статуса.
Резерв сохраняется, submit не повторяется. Прочие unknown (сеть, неопределённая
отправка/ответ) по-прежнему допускают уточнение статуса. Регрессия в
`test/codex.test.js` проверяет единственный опрос на worker, общую БД,
восстановление на другом worker, отсутствие повторного POST и held;
`test/codex-worker-client.test.js` проверяет границу идентификатора.

## Исправление RPC-таймаутов

В веб-интерфейсе Codex во время задания показываются этап и прошедшее время
(`submitting`, затем `generating`). При завершении worker сохраняет
`startedAt`, `completedAt` и `durationMs`; итог и история выводят длительность
генерации. Для старых записей время берётся из `createdAt`, если отдельный
`startedAt` отсутствует.

При запуске media-сервиса незавершённые Codex-задания (`submitting`, `running`,
`unknown`) сбрасываются в `cancelled`; резерв по ним освобождается, а история
показывает отмену при обновлении сервиса. Это предотвращает блокировку новой
генерации после обновления или перезапуска контейнера.

RPC timeout больше не завершает общий процесс; default 60000 мс, настройка
MEDIA_CODEX_RPC_TIMEOUT_MS. Поздние thread/start очищаются без turn, поздние
turn/start прерываются по ID. Session выдаётся только после initialize.
Диагностика: rpc_timeout/process_stop/process_exit без секретов. Unknown без
повторов. Регрессии: изоляция таймаута, поздние turn/thread, timeout unsubscribe.

Проверка после исправления новой волной 256: 61 PNG, 195 failed, 0 unknown.
Обрыв на 15 с устранён, процессы штатно закрыты после теста; высокая доля
отказов остаётся открытой проблемой, 2 × 128 не подтверждена как рабочая мощность.
Метрики и evidence: docs/codex-capacity.md.

Повтор без изменений 17:18 UTC: 60/256 PNG, 196 failed, 0 unknown,
0,640 PNG/с за 93,77 с. Почти совпал с 61/256 предыдущей волны.
Высокая доля отказов воспроизводится, RPC-обрыва нет; причина отказов неизвестна.

## Причина массовых failed — установлена

Read-only logs_2.sqlite: 196/196 отказов повторного опыта и 195/195 предыдущего
завершились 429 Too Many Requests после внутренних retry Codex. Retry-After
2–53 с. WebSocket ранее отвечал 403, Codex переходил на HTTP. Точная область
лимита неизвестна; признаков exhausted quota в проанализированных записях нет.
Адаптер не повторяет задания, но Codex делает внутренние retry/fallback.
Нужен общий pacing/лимит до отправки на аккаунт; рост числа процессов не
устраняет throttling. Подробные подсчёты и evidence: docs/codex-capacity.md.

CLI exec 256 (17:26 UTC): 9 подтверждённых PNG, 41 failed, 206 неизвестных
итогов вследствие HTTP-таймаутов наблюдателя. Peak memory 13,53 ГиБ, без OOM;
cleanup завершил оставшиеся процессы. Не сравнивать 9/256 как истинную
успешность провайдера. App-server оставлен основным. Подробности: docs/codex-capacity.md.

GPT-5.6 Sol: 128/128 PNG на одном app-server, medium + fast, 1,690 PNG/с,
0 ошибок и 0 unknown. Пик памяти 2,81 ГиБ. Это короткая волна; устойчивый
предел и 256 Sol не проверены. Evidence: docs/codex-capacity.md.
# Диагностика ошибок — 2026-09-27

Дополнение 2026-10-01: worker записывает исходный Error выполнения/сохранения
в ai_logger (`codex-worker.run.error`, `codex-worker.persist.error`), независимо
от успешности доставки; исходный стек не заменяется. Образ содержит
`system-errors.js`, Compose передаёт настройки логгера с ролью `codex-worker`.
Код ошибки проходит worker JSON → billing → историю (`errorCode`).
При пустом image failure сохраняется последняя ошибка внутреннего retry,
если нет итоговой неповторяемой ошибки; successful turn её игнорирует.
Если технической причины всё ещё нет, финальный agentMessage хранится отдельно
от Error.message и добавляется только в ошибку для владельца, без передачи
в центральный журнал. Проверки: codex-errors и codex-app-server (поздний retry,
owner-only explanation, исходный Error, отказ логгера без изменения результата).

`codex-errors.js` формирует ограниченное сообщение из разрешённых полей
ошибки провайдера с удалением секретов и бинарных данных. App-server проверяет
status/failure imageGeneration до декодирования PNG, сохраняет ошибки RPC,
turn/error и turn/completed; willRetry не завершает пользовательское задание.
Exec сохраняет ошибки JSONL. При отсутствии PNG доступен финальный текст
модели. Worker и billing передают очищенное сообщение в историю и системный
журнал; Vue показывает его владельцу задачи без требования роли admin.
Unknown и отсутствие автоматического платного повтора сохраняются.
Покрытие: test/codex-errors.test.js, test/codex-app-server.test.js,
test/codex.test.js. Старые ошибки не переписываются.
