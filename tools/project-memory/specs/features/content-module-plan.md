# Локальный план: единый модуль контента

Статус: реализован и мигрирован локально 2026-09-22. Физическое удаление и GC
по-прежнему вынесены в отдельный будущий этап.

## Цель

Все новые изображения, видео и другие пользовательские файлы проходят через
единый модуль контента и хранятся в приватном S3. PostgreSQL хранит владельца,
метаданные, состояние сохранения и связи файла с генерациями и чатами, но не
байты файла и не машинные локальные пути.

Готовое поведение:

- каждый новый результат генерации получает новый UUID;
- перегенерация создаёт новый файл, новый UUID и новую запись владельца;
- повтор сохранения того же результата использует прежний UUID;
- файл сохраняется под tenant-префиксом пользователя;
- чат продолжает определять расположение результата через `chatId` и время
  создания записи; отдельные координаты файла не вводятся;
- после перезапуска результат доступен через приложение независимо от локального
  диска конкретного экземпляра сервиса.

## Принятые решения

### Объекты S3

Ключ каждого нового объекта:

```text
accounts/<account-id>/content/<asset-uuid>
```

S3 остаётся приватным. Исходное имя не входит в ключ и хранится только как
метаданные. UUID является идентификатором файла, но не разрешением на доступ:
каждое чтение проверяет владельца через PostgreSQL.

Новая генерация и перегенерация всегда создают новый asset. Повтор фоновой
загрузки является продолжением сохранения существующего asset и не создаёт
новый UUID. Дедупликация одинаковых байтов на первом этапе не выполняется.

### Каталог в PostgreSQL

Добавить нормализованный каталог `content_assets`:

- `id uuid` — идентификатор файла;
- `account_id uuid` — владелец;
- `storage_key text` — ключ приватного объекта;
- `original_name text` — имя для интерфейса и скачивания;
- `mime_type text`, `size_bytes bigint`, `sha256 text` — проверенные свойства;
- `status text` — минимум `saving`, `ready`, `failed`, `missing`;
- `created_at`, `updated_at` — даты жизненного цикла;
- сведения о происхождении, достаточные для диагностики и безопасного повтора,
  без секретов и больших payload в БД.

Уникальность обеспечивается UUID и первичным ключом. `sha256` используется для
проверки целостности, а не как идентификатор или глобальная дедупликация.

### Связи с генерациями и чатами

Добавить нормализованные связи результата/исходника с asset: владелец,
идентификатор записи генерации, `asset_id`, роль `source` или `result` и порядок
в наборе. Владелец asset и владелец связанной записи обязаны совпадать.

Текущий механизм чатов сохраняется:

- генерация содержит `chatId` и при необходимости `projectId`;
- лента сортирует записи по времени создания;
- интерфейс сам рассчитывает расположение карточек;
- позиция прокрутки остаётся состоянием интерфейса.

Координаты `x/y` и отдельная модель размещений на холсте в этот план не входят.
Если такой холст появится, его размещения будут отдельными сущностями, а не
свойствами файла.

## Рабочий поток

### Новый результат

1. Провайдер подтверждает готовый результат.
2. Сервер создаёт UUID asset, запись `saving`, связь с генерацией и устойчивое
   задание сохранения.
3. Результат появляется в чате с состоянием сохранения. Для раннего превью
   используется только источник, который можно повторно получить до завершения
   S3-загрузки.
4. Фоновый исполнитель потоково переносит файл в S3 с тем же UUID.
5. Исполнитель проверяет размер и SHA-256, затем переводит asset в `ready`.
6. Все последующие просмотры и скачивания идут через авторизованный endpoint
   приложения, поддерживающий byte ranges для видео.

Ошибка S3 меняет состояние сохранения и запускает повтор того же задания. Она
не запускает повторную платную генерацию и не создаёт новый UUID. Состояние
генерации и состояние сохранения файла учитываются отдельно.

Задание и сведения, необходимые для повтора, должны переживать перезапуск. До
этого нельзя считать раннее превью доказательством сохранённого файла. Для Kie
можно повторно использовать исходную HTTPS-ссылку, пока она действительна; для
результата, который нельзя восстановить у провайдера, байты должны быть
зафиксированы в устойчивом staging до показа состояния `ready`.

### Новый исходник

Пользовательская загрузка сразу получает asset UUID и проходит тот же цикл
`saving` → `ready`. Генерация принимает `asset_id`, проверяет владельца и читает
байты через модуль контента. Готовый результат разрешено повторно выбрать как
исходник без повторной загрузки в S3; создаётся новая связь `source` с тем же
asset.

## Граница модуля

`ContentService` становится единственной точкой работы приложения с файлами:

- создание asset и приём загрузки;
- импорт результата провайдера;
- получение метаданных;
- авторизованное потоковое чтение и byte ranges;
- постановка и повтор заданий сохранения;
- проверка целостности и сверка БД с S3.

Существующий S3-адаптер остаётся транспортным слоем и не принимает решений о
владельце, чатах или генерациях. Модули Kie, Codex, HTTP и пользовательских
исходников обращаются к файлам только через `ContentService`.

## Инварианты

- файл `ready` существует в S3 и соответствует записанным размеру и SHA-256;
- пользователь читает только asset своего аккаунта, включая admin-просмотр
  другого аккаунта через существующий явно выбранный scope;
- новая генерация создаёт новый UUID, а retry сохранения сохраняет старый;
- ошибка сохранения не меняет финансовый результат генерации и не повторяет
  запрос провайдеру;
- ни один новый постоянный файл не зависит от локального пути экземпляра;
- удаление сообщения или генерации не выполняет немедленное физическое удаление
  объекта;
- резервная копия охватывает и PostgreSQL, и S3.

## Проверка и критерии готовности

- новый исходник, результат Kie и изображение Codex получают UUID и `ready`;
- перегенерация создаёт другой UUID;
- повтор одного задания после сетевой ошибки не создаёт второй asset и не
  запускает вторую генерацию;
- после перезапуска незавершённое сохранение возобновляется либо явно переходит
  в диагностируемое `failed`/`missing`;
- другой аккаунт не может читать файл по известному UUID;
- обновление страницы и открытие того же чата восстанавливают изображения и их
  порядок без координат;
- видео поддерживает частичное чтение и скачивание;
- legacy-записи продолжают открываться во время перехода;
- сверка каталога с S3 находит отсутствующие и лишние объекты без автоматического
  удаления;
- целевые тесты, `pnpm check`, обязательная пересборка Compose, healthy-сервисы и
  `http://127.0.0.1:3000/api/health` подтверждены на свежих контейнерах.

## Вне первого этапа

Глобальная или пользовательская дедупликация, публичные URL бакета, CDN,
отдельный домен хранилища, координатный холст, автоматическое физическое удаление
и release-инфраструктура не входят в этот план без отдельного решения владельца.
Production-защита, CDN, versioning, Object Lock, backup и восстановление вынесены
в [план CDN и Storage](cdn-storage-production-plan.md).

## Фактическая миграция и проверка

Миграция 2026-09-22 обработала 13 исходников и 33 результата Codex: 25 assets
получили состояние `ready`, 21 — `missing`, один доступный локальный файл был
дозагружен, создано 53 связи. Повторный аудит подтвердил 46 записей каталога,
нулевое число отсутствующих `ready`-объектов, несовпадений размера и сиротских
объектов. Команды миграции и аудита входят в Docker-образ.
