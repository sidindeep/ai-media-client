# Два режима Codex и сравнение нагрузки

Дата: 2026-09-18. Реализованы `exec` и `app-server` за одним HTTP worker.
Это два транспорта адаптера, а не пользовательские Skills.

## Выбор режима

В окружении worker задать `MEDIA_CODEX_TRANSPORT=exec` или
`MEDIA_CODEX_TRANSPORT=app-server`. По умолчанию используется `app-server`. `exec` сохранён как ручной резерв
и без явного выбора не запускается; автоматического fallback нет.
Compose передаёт настройку из `.env` в сервис `codex`; встроенный worker
Bothost читает её из окружения приложения. Изменения исходников требуют
пересборки по [инструкции Codex](codex.md); смена окружения — пересоздания контейнера.
Приватный `/health` worker сообщает выбранный `transport`.
Режим выбирается сервером для worker целиком, не полем пользовательского POST.

- `exec`: отдельный `codex exec` для каждого запроса; процесс завершается с задачей.
- `app-server`: пул из двух долгоживущих процессов, каждый запускается лениво;
  независимые ephemeral threads выполняются параллельно через JSON-RPC/stdio.
  На процесс допускается 128 активных заданий (256 на worker), остальные ждут
  в FIFO-очереди. Выбор — процесс с наименьшим числом активных заданий.
  MEDIA_CODEX_POOL_SIZE (1..32, default 2) и MEDIA_CODEX_PROCESS_CONCURRENCY
  (1..128, default 128) задаются сервером. Очередь хранится в памяти; её ожидание
  не входит в таймаут генерации. При остановке ожидающие задания отменяются.
  Ошибка одного процесса не останавливает второй; задания не переносятся повторно.
  Каждому заданию соответствует отдельный thread и один turn. Чаты пользователей
  не объединяются. Вспомогательные процессы Codex по-прежнему возможны.
- Оба режима используют существующий серверный аккаунт и `CODEX_HOME`.
  Несколько аккаунтов и диспетчер между ними в эту реализацию не входят.
- Публичные запросы, кредиты, история и выдача PNG остаются общими. Автоматического
  переключения транспорта или повторной генерации при ошибке нет.

App-server проверен с CLI 0.155.0. Его параметры сверены со схемой, которую
генерирует эта версия (`codex app-server generate-json-schema`), а не только
с последней документацией. Протокол: [OpenAI Docs](https://learn.chatgpt.com/docs/app-server).

## Изоляция, отказы и завершение

App-server получает тот же ограниченный набор переменных среды, что и exec:
без БД, OAuth и ключа Kie. Рабочий каталог пустой и временный. Thread создаётся
с `sandbox=read-only`, `approvalPolicy=never`, без чтения инструкций проекта;
shell/browser/apps/hooks и прочие интеграции отключены. Генератор изображений
и code mode включаются только для image-thread. Интерактивные запросы сервера
отклоняются. Пути файлов из текста модели и событий item не используются:
PNG читается только из `generated_images/<trusted-thread-id>` и валидируется.

В CLI 0.155.0 app-server не поддерживает `--ignore-user-config`, доступный exec.
Поэтому новый режим отказывается стартовать при наличии `CODEX_HOME/config.toml`,
чтобы не наследовать произвольные MCP/config overrides. Не удалять пользовательский
config автоматически: использовать exec либо специально подготовленное хранилище
авторизации без него. Это ограничение новой реализации, не общее требование Codex.

Подтверждённый неуспех turn даёт `fail`. Потеря процесса/stdio, отсутствие ответа
RPC и таймаут ожидания дают `unknown`: резерв сохраняется и нужна сверка.
Таймаут пытается прервать только свой turn, не останавливая общий процесс.
MEDIA_CODEX_RPC_TIMEOUT_MS задаёт ожидание RPC (по умолчанию 60000 мс).
Общий предел текста 180 секунд, изображения 300 секунд. Поздний thread/start
очищается через unsubscribe без генерации, поздний turn/start — через interrupt.
Поздние RPC-ответы учитываются до 300 секунд после таймаута, не более 1024
записей на процесс. Без ответа провайдера остановку генерации гарантировать
нельзя; unknown не повторяется. Таймаут initialize закрывает ещё не готовый
процесс. Реальная потеря stdio/процесса делает его активные задания unknown.
Журнал содержит rpc_timeout с именем метода и process_stop/process_exit
с причиной, без параметров запросов и сырого ответа провайдера.
Новый запрос после падения может запустить новый процесс, старые запросы не повторяются.
При остановке worker завершается вся группа процессов app-server.
После смены серверного аккаунта через вход перезапустить worker, чтобы завершить
прежний app-server с его состоянием авторизации.

После завершения thread выполняется `thread/unsubscribe`. Это не обещание
немедленного освобождения всей памяти: текущая документация описывает grace period
до 30 минут. Накопление threads нужно измерять длительным тестом.
Общий часовой кеш PNG/Base64 worker также сохраняется в обоих режимах.

## Воспроизводимый ограниченный A/B-прогон

Из корня проекта, после сборки локального Compose и входа Codex:

```powershell
node scripts/benchmark-codex-transports.cjs --docker --live
```

Команда выполняет реальные генерации и требует заранее выделенного бюджета.
Максимум за один запуск: 6 текстов и 6 изображений суммарно, по 3 на транспорт.
Вариант `--text-only` ограничивается 6 текстами. Новые отправки прекращаются
при первой ошибке; уже запущенная пара завершается. Повторных отправок нет.
Каждый повтор команды расходует новый бюджет, предыдущий лимит его не разрешает.

Модель/effort/speed берутся из `uiDefaults` текущего каталога и валидируются.
Для каждого типа и режима выполняется одна одиночная генерация и одна параллельная
пара. Промпт одинаков внутри типа; текст: три предложения о саде; изображение:
акварельное красное яблоко. Секреты и содержимое результатов в отчёт не попадают.
Вывод сохраняется в `artifacts/load-tests/transport-<UTC>/events.jsonl`, вне Git.

Это вызов адаптеров напрямую внутри локального worker-контейнера, без веб-кошелька,
PostgreSQL, HTTP-опроса и часового кеша результатов. Внутренние кредиты приложения
не списываются; расходуется серверный аккаунт Codex. Это не сквозной нагрузочный
тест из [основного плана](codex-load-test-plan.md).

Измеряется длительность до получения текста или валидированного PNG; CPU —
разница `usage_usec` cgroup, память — RSS/PSS дерева тестового процесса и
`memory.current` контейнера, выборка 200 мс. PSS учитывает долю разделяемых страниц.
App-server остаётся работающим во время exec-волн, поэтому абсолютные пики
контейнера нельзя напрямую объявлять памятью одного транспорта. Они сохранены
для диагностики; нужно учитывать исходный уровень и удерживаемое состояние.
CPU включает фон контейнера и сборщик метрик, а не только модельный клиент.

## Фактический результат первого прогона

CLI 0.155.0; GPT-5.5 / medium / Fast; локальный Compose; 2026-09-18.
Все 12 запросов успешны: по 3 текста и 3 PNG на транспорт. Свидетельство:
`artifacts/load-tests/transport-2026-09-18T16-05-50-682Z/events.jsonl`.
После завершения в контейнере остались только штатные init и worker;
процессов benchmark/app-server/генераций не осталось.

| Метрика | exec | app-server | Наблюдение |
| --- | ---: | ---: | --- |
| Среднее время текста, с | 4,92 | 4,10 | app-server меньше на 16,8% |
| Время волны из 2 текстов, с | 4,85 | 3,46 | 24,74 против 34,70 результатов/мин в одной волне |
| CPU-секунд на текст | 1,19 | 0,59 | около −50% локального CPU |
| CLI-токенов на текст | 6 771 | 8 756 | app-server больше на 29,3% |
| Среднее время PNG, с | 27,88 | 26,36 | app-server меньше на 5,4% |
| Время волны из 2 PNG, с | 27,95 | 26,93 | 4,29 против 4,46 результатов/мин в одной волне |
| CPU-секунд на PNG | 2,10 | 1,11 | около −47% локального CPU |
| CLI-токенов на PNG | 20 592 | 24 183 | app-server больше на 17,4% |

Холодный одиночный текст app-server занял 5,42 с против 5,09 с у exec.
Ускорение проявилось в тёплой параллельной волне, а не во всех запросах.
У прогретого app-server прирост PSS при паре текстов составил примерно 25 МиБ,
при паре изображений — 41 МиБ. У exec соответствующий прирост над исходным
уровнем — 117 и 161 МиБ. Эти дельты не включают постоянную память app-server:
первый запуск поднял PSS всего дерева примерно с 28 до 203 МиБ, в конце прогона
он был около 292 МиБ. Долговременная устойчивость памяти не измерена.

Токены включают системный контекст конкретного режима; одинаковый пользовательский
промпт не делает полный вход одинаковым. Доля cached input различалась.
Нельзя считать эту разницу прямой разницей денег или доступных генераций по подписке.
Отдельная стоимость инструмента изображений в этих счётчиках не представлена.

## Что выгоднее

По этому пилоту app-server перспективнее для плотного текстового потока и экономии
CPU. Для изображений измеренный выигрыш времени небольшой; значительная часть
ожидания приходится на удалённую генерацию. Exec сообщил меньше CLI-токенов
и освобождает свои процессы после каждого задания. По деньгам победитель не
установлен: нужны фактическая тарификация аккаунта и стоимость ресурсов хостинга.

Иллюстрация масштаба, не прогноз мощности: при 1 000 одинаковых результатах
наблюдаемая разница CPU составила бы около 597 CPU-секунд для текста и
992 CPU-секунд для PNG. Разница CLI-токенов — около +1,98 млн и +3,59 млн
соответственно у app-server. Перевод в рубли без модели оплаты некорректен.

Размер выборки — 3 результата на сочетание типа и транспорта. Одной волны на
параллельность недостаточно для устойчивого throughput, p95 и безопасного лимита.
Следующее исследование: чередующиеся независимые A/B-прогоны, одинаковый холодный/
тёплый режим, измерение дерева каждого транспорта отдельно, затем ≥90 минут
на выбранной ступени со сбором кеша/диска/резервов по основному плану.
