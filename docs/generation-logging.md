# Журнал генерации

Логирование включено автоматически при запуске.

## Личный журнал аккаунта

В веб-версии страница **История расходов** показывает отдельный **Журнал генераций**.
Он объединяет Kie.ai, RouterAI и Codex и фильтруется по провайдеру. Счётчики
«Создано генераций» и «Попыток отправки провайдеру» различают локальные задачи
и реальные попытки POST. Записи хранятся в PostgreSQL как отдельные события
`media_records` с namespace `generation-journal` и `account_id`; удаление карточки
из истории их не удаляет. API `getGenerationJournal` доступен только владельцу
аккаунта и администратору при просмотре выбранного аккаунта. Обычному
пользователю не возвращаются внешние task ID, провайдерская себестоимость и
диагностическая ошибка. Промпты, ответы, ключи и содержимое файлов в личный
журнал не записываются. События пишутся только для новых и изменённых задач;
старый файловый лог и ранее удалённые задачи задним числом не восстанавливаются.

События Kie отражают переходы состояния, включая `submitting`; RouterAI и
Codex фиксируют создание, `send_start` перед вызовом провайдера и результат.
`send_start` означает попытку отправки, а не подтверждённое принятие или
списание провайдером. По RouterAI-видео дополнительно сохраняется `accepted`
с внешним ID. История расходов отдельно показывает фактические списания.

- Windows: `%APPDATA%/ai-media-client/logs/generation.jsonl`; кнопка **Открыть журнал** в настройках приложения.
- Web/Telegram: `<MEDIA_DATA_DIR>/logs/generation.jsonl` в корне проекта, обычно `data/service/logs/`. Docker использует тот же подключённый каталог данных.

JSONL: одно событие в строке. Поля `time`, `sessionId`, `sequence`, `requestId`, `jobId`, `taskId`, `model`, `event`, `details` связывают запрос пользователя, локальную очередь и удалённую задачу. До получения ID провайдера `taskId` отсутствует. У событий вне задачи (запуск, баланс, управление очередью) нет `jobId`.

Журнал содержит запрос генерации и проверку параметров, подготовку и проверку исходников, загрузки, фактические HTTP-запросы/ответы Kie, повторные попытки безопасных HTTP-операций, каждый опрос и смену статуса, исходные `failCode`/`failMsg`, длительности этапов и скачивание результата. Telegram дополнительно записывает запуск, ID обработанного update и результат вызова Bot API. Платные отправки автоматически не повторяются.

Неожиданная ошибка account API записывается как `service.request.error`: метод, путь, имя RPC и очищенная ошибка без тела запроса, cookie и ключей. В браузере при этом остаётся общее безопасное сообщение.

Промпты и параметры сохраняются: это локальная диагностика, не публичный файл. Ключи авторизации, токены, cookie, пароли и параметры URL скрываются; содержимое бинарных файлов не записывается. Текстовые HTTP-ответы ограничены 64 КиБ, отдельные строки — 32 КиБ, массивы — 100 элементами. Усечённый HTTP-ответ отмечается `truncated`. Для медиа записываются метаданные.

Ротация: текущий файл и до четырёх предыдущих (`.1`…`.4`), примерно по 5 МиБ. Логи не отправляются наружу и не попадают в Git или Docker-образ. Если диск недоступен, ошибка выводится в stderr один раз; работа генерации продолжается.

Старые запросы задним числом не восстанавливаются. Для расследования нужны файлы журнала от момента запуска до результата. Ошибку провайдера можно найти по `taskId` или `jobId`, затем прочитать события этого запроса по `requestId`.

Стоимость: task.enqueued содержит cost.estimate (кредиты/рубли, источник, дата тарифа); task.cost после success/fail — отдельные estimate и actual. Неизвестное списание остаётся null, включая ошибки генерации. Курс берётся из записи задачи.

Структурированная ошибка errorInfo содержит категорию, код/сообщение Kie, безопасное описание, действие, возможность ручного повтора, stage и taskId. Поле automaticRetry всегда false: автоматической повторной платной генерации нет. HTTP 400 без уточнения не классифицируется как нарушение контента; неизвестные причины остаются unknown. Старые записи получают пояснение при отображении без изменения истории.
