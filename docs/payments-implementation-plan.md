# План реализации платежей для AI Media Client

Дата: 2026-09-22. Статус: базовый поток P0–P4 реализован частично; локальный DEBUG checkout работает через test-заглушку, настоящий sandbox не проверен.
Исполнитель: GPT-5.6 Sol, reasoning effort medium. Модель сама по себе не
заменяет проверки денежных инвариантов. Этапы выполнять последовательно.

Архитектура и точные инварианты:
[платёжный модуль](../tools/project-memory/specs/features/payments-module.md).
Текущее поведение: [аккаунты и кредиты](accounts-and-credits.md).

Реализованы контракты, schema v5, payment attempt/outbox, адаптер ЮKassa,
каталог и snapshot заказа, HTTP facade, product inbox, атомарное начисление,
return-state UI и изолированный контейнерный тестовый target. Остаются durable
command worker для неизвестного результата, webhook raw inbox, leases/fencing,
многосоединительные PostgreSQL-тесты, refunds, admin/metrics и живой sandbox.
Для DEBUG добавлен `yookassa-stub`: карточка создаёт заказ и pending-платёж через
тот же payment module, но не открывает платёжную страницу, не принимает webhook,
не списывает деньги и не начисляет кредиты. Он разрешён только в test-среде.
Чтобы показать карточки в локальном Compose, установить в игнорируемом `.env`
`MEDIA_PAYMENTS_ENABLED=true`, `MEDIA_SALES_ENABLED=true`,
`MEDIA_PAYMENTS_ENVIRONMENT=test`, `MEDIA_PAYMENTS_PROVIDER=yookassa-stub`.
Чеклисты ниже сохраняют полный критерий этапа; этап не считается завершённым,
пока все его пункты и приёмка не подтверждены.

## Результат

Пользователь выбирает пакет кредитов, получает страницу оплаты, оплачивает
и видит однократное начисление, включая случаи повтора уведомлений и перезапуска.
Платёжный модуль работает внутри приложения, общается с провайдерами и не
знает содержимое покупки. Будущий переход на отдельный сервис меняет транспорт,
развёртывание и владение БД, сохраняя денежные и продуктовые контракты.

План разделяет четыре результата:

1. Ядро и продуктовый поток проверены на управляемом тестовом провайдере.
2. Реальный провайдер проверен в его sandbox, реальные продажи выключены.
3. Пилот реальных продаж включён после входных решений и соответствующей проверки.
4. Выделение в отдельный сервис — будущее развитие, не часть текущего MVP.

| Вопрос | Решение / что требуется | Какие этапы блокирует |
| --- | --- | --- |
| Граница | Карточки/заказы/кредиты в продукте, деньги/провайдеры в payments | Решено |
| Развёртывание | Один текущий проект, payments внутри Node.js | Решено |

| Предложения | Название, цена, валюта, кредиты; не путать с расходным прайсом моделей | Публикация P6/P8 |

- Делать один целостный этап; крупный этап дробить на перечисленные задачи.
  Не начинать UI и провайдер одновременно с неустойчивой моделью денег.
- Обновлять чеклист, реализованные контракты и доказательства проверки после
  этапа; отдельно указывать TODO, допущения, blocker и следующий этап.
- Не считать тестовый fake доказательством работы реального провайдера.
  Не выполнять реальных списаний, возвратов или генераций для проверки без

  уже имеющуюся авторизацию на изменение этой БД. Если её нет, получить её по
  `AGENTS.md`; тесты на изолированной БД продолжаются независимо.
- Коммит/push, hosting deploy и выделение сервиса не входят в данный план запуска.

- [ ] Проверить `.dockerignore`: test target действительно получает test/,

## P1. Денежное ядро и PostgreSQL-хранилище

Зависимости: P0. Результат: создание/чтение платежа без внешней оплаты.

- [ ] Создать чистые money/state функции: safe integers, разрешённые валюты,
  отдельный unknown, проверки неизменяемых полей и терминальных переходов.
- [ ] Реализовать собственные SQL repositories и версионированные миграции
  payment_* по спецификации. Не добавлять FK к media_accounts/media_orders.
- [ ] Реализовать createPayment/getPayment/getPaymentByOrder/getCapabilities,
  scoped client/environment auth и устойчивую идемпотентность.
- [ ] Добавить unique constraints, индексы ожидающих операций, canonical hash.
  Команда и попытка сохраняются до внешнего действия.
- [ ] Добавить архитектурный тест: payments не импортирует продуктовые модули
  и не читает их SQL-таблицы.

Приёмка: повтор создания возвращает тот же payment; изменённый payload — conflict;
одинаковые ключи разных клиентов изолированы; внешние ID уникальны по merchant,
provider и environment; ошибка транзакции не оставляет половину операции.
Реальная конкуренция минимум двух PostgreSQL-соединений проверена отдельно.

## P2. Провайдерский цикл, webhook, сверка и outbox

Зависимости: P1. Результат: надёжный денежный поток на fake provider.

- [ ] Определить ProviderAdapter: capabilities, create/get payment,
  verify/normalize webhook, create/get refund, classifyError.
  Сохранить исходный provider key; mapping статусов принадлежит адаптеру.
- [ ] Реализовать внешний вызов вне SQL-транзакции, фиксацию результата,
  unknown и восстановление после потери ответа. Provider account закреплён
  за попыткой, смена настроек не меняет провайдера уже созданного платежа.
- [ ] Реализовать durable webhook inbox, аутентификацию адаптером, обработку
  duplicate/out-of-order. Быстрое уведомление до ответа create восстанавливается
  по сохранённой корреляции или откладывается, не приписывается чужому заказу.
- [ ] Обновлять payment state + outbox в одной локальной транзакции.
  Dispatcher доставляет событие повторно до подтверждённого commit потребителя.
- [ ] Реализовать leases/fencing/backoff, reconciler, shutdown/restart recovery.
  Учесть одновременную работу локального и hosted экземпляров с общей БД.

Приёмка: crash в каждой точке «до POST / после POST / до commit / после commit /
до ACK» не теряет успешную оплату и не создаёт повторный внешний POST с новым
ключом. Unknown не превращается в отказ по таймеру; потерянный webhook обнаруживает
reconciler. Вне provider idempotency window неопределённость уходит на разбор.

## P5. Первый реальный провайдер в sandbox

Зависимости: P4 и выбранный провайдер с тестовым магазином.

### Проверенная возможность: тестовый магазин ЮKassa

Исследовано 2026-09-22 по ссылке владельца; магазин не создан, credentials не
получены, интеграционные запросы не выполнялись. Реализацию по-прежнему
предполагается передать Sol Medium. Создание магазина возможно уже сейчас,
параллельно P0–P4; полный продуктовый прогон требует реализации этих этапов.

- Тестовый магазин доступен до завершения регистрации/заключения договора.
  [Прямая регистрация](https://yookassa.ru/joinups?createTestShop=true) позволяет
  выбрать тестирование; в существующем кабинете используется «Добавить магазин».
- Нужны shopId и секретный ключ тестового магазина из «Интеграция — Ключи API».
  Ключ хранить только в игнорируемом локальном secret/env-файле или secret store;
  не включать в план, source, чат, логи и Git.
- Деньги не списываются. Предлагаемый первый сценарий — страница оплаты ЮKassa,
  тестовая банковская карта и одностадийная оплата с `capture=true`.
  Проверка чеков доступна через тестовую онлайн-кассу.
  Источник: [тестовый магазин](https://yookassa.ru/docs/support/merchant/payments/implement/test-store).
- Sandbox поддерживает карты и ЮMoney, базовые платежи/возвраты/уведомления.
  Остальные способы оплаты проверяются в настоящем магазине. В объекте тестового
  платежа `test=true`: адаптер обязан сверять его с ожидаемой средой, а также
  магазин, сумму и валюту. Нельзя считать sandbox доказательством работы всех
  live-методов. Источник: [API testing](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).
- Для webhook нужны HTTPS, порт 443/8443 и TLS >= 1.2. При HTTP Basic Auth
  события настраиваются в кабинете, не через OAuth webhook API. Начальный набор:
  `payment.succeeded`, `payment.canceled`, `refund.succeeded`; неожиданное
  `waiting_for_capture` не даёт выдачу покупки и требует сверки.
- Нормальная квитанция приёма — HTTP 200; при другом статусе ЮKassa повторяет
  доставку до 24 часов от события. Сначала сохранить событие устойчиво.
  Подлинность проверять серверным чтением объекта через API магазина; проверка
  исходного IP возможна дополнительно при доверенной proxy-конфигурации.
  Не придумывать обязательную HMAC-подпись webhook.
  Источник: [входящие уведомления](https://yookassa.ru/developers/using-api/webhooks).

Для первой проверки create/get/checkout публичный webhook не обязателен:
сервер может сверить объект через API. Это частичная интеграционная проверка,
а завершённый P5 обязательно проверяет и настоящую доставку webhook.
Будущий URL вида `/api/payments/webhooks/yookassa/test` — предлагаемый маршрут,
сейчас не существует. Перед внесением URL в кабинет он должен быть реализован
и доступен в согласованном изолированном sandbox окружении. Не направлять
тестовую оплату в кошельки общей debug БД. Выбор провайдера для live остаётся
отдельным решением; sandbox не требует утверждения реальных цен пакетов.

### Задачи реализации

- [ ] Реализовать адаптер, нормализацию ошибок, ограничения timeout и безопасные логи.

Приёмка: подтверждены штатная оплата, отмена, повтор уведомления, потеря

- [ ] Реализовать monetary refund state machine: резерв refundable amount,
  stable key, unknown, reconciliation; параллельные возвраты не превышают оплату.
- [ ] Под выбранную политику реализовать продуктовый резерв/компенсацию кредитов

- [ ] Обработать внешний refund/dispute: обнаружение, журнал, review_required,

- [ ] Добавить admin список платежей/unknown/outbox backlog/paid-but-unfulfilled,

- [ ] Добавить диагностику workers, безопасные логи и метрики из спецификации;
  документацию восстановления после crash и недоступности провайдера.

Приёмка: параллельные/повторные/неопределённые возвраты не возвращают лишнее;
нельзя потратить зарезервированные к возврату кредиты; провайдерский отказ
освобождает продуктовый резерв, unknown удерживает; баланс не уходит ниже held.
При отсутствии политики этап явно частичный, реальные возвраты выключены.

## P8. Проверка перед реальными продажами

Зависимости: P0–P7 и входные решения. Это отдельный запуск после реализации.

- [ ] Пройти матрицу ниже на свежем Docker runtime и настоящем изолированном
  PostgreSQL. Сверить отсутствие межмодульных SQL зависимостей и утечек секретов.
- [ ] Проверить backup/restore платежных данных и сохранение dedup keys.
- [ ] Подтвердить опубликованные цены, merchant, валюту, checkout/receipt
  настройки и рабочий путь возвратов. Отделить test от live.
- [ ] Подготовить конкретный live-пилот: сумма, аккаунт, ожидаемое начисление,
  контроль возврата, предел затрат. Выполнять только при явном разрешении.
- [ ] Включить продажи ограниченно; сверить деньги, заказ и credits ledger.
  Отключение продаж прекращает новые checkout, но оставляет webhook/reconcile/
  выдачу/возврат уже существующих операций. Не делать общий kill switch workers.

Готовность MVP: провайдер подтверждает оплату; пользователь получает ровно одну
покупку; известны и проверены пути отказа/восстановления/возврата; диагностика
позволяет найти оплаченный, но не выданный заказ. Не объявлять live готовность
по одному health или имитации платежа.

## Обязательная матрица проверки

| Сценарий | Ожидаемое доказательство |
| --- | --- |
| Двойной checkout и повтор ключа с другим телом | Один payment; изменённое тело даёт conflict |
| Конкурентные webhooks, разные eventId одного успеха | Одна выдача и purchase; UNIQUE + реальная concurrency |
| Один provider payment под разными аккаунтами | Второй эффект запрещён глобальной привязкой |
| Чужие client/order/environment | Нет чтения/зачисления; test и live не смешиваются |
| Неверная сумма/валюта/merchant и поддельный webhook | Нет успеха/выдачи; безопасная диагностика |
| Webhook до ответа create и поздний pending после success | Корректная корреляция; успех не откатывается |
| Timeout после принятия POST | Unknown; сверка прежней операции; нет нового provider key |
| Истёкшее окно provider idempotency | Нет слепого повторного POST; review |
| Crash до/после каждого commit и ACK | Устойчивая доставка; одна проводка |
| Два worker экземпляра и истёкший lease | Fencing, безопасный повтор, нет потери задания |
| Provider API недоступен | Студия работает, checkout объясняет задержку |
| Потерянный webhook | Reconciliation восстанавливает факт оплаты |
| Несколько refunds одновременно | Сумма succeeded + pending + unknown <= оплаченной |
| Refund раньше success / возврат после расходования | Нет ошибочной выдачи/отрицательного баланса; policy/review |
| Изменённая цена и подменённый браузерный payload | Snapshot сохранён, новое предложение явно показано |
| Закрытый браузер, refresh, возврат по success URL | Выдача не зависит от браузера; UI читает истинный статус |
| Неверная версия события / повтор eventId с другим hash | Денежного эффекта нет, событие доступно для разбора |
| Повторное применение миграций и старые accounts | Нет потери записей; grant/reserve/settle работают как раньше |

## Проверки каждого этапа

До финальной проверки после любого целостного пакета изменений обязательно:

```powershell
docker compose up -d --build
docker compose ps
Invoke-RestMethod -Uri http://127.0.0.1:3000/api/health
```

Дождаться healthy у `media` и `codex`, проверить `ok` и состояние БД.
При сбое читать только свежие логи сервисов этого Compose-проекта.
Далее запустить относящиеся к этапу контейнерные проверки по команде,
добавленной и проверенной в P0. При изменении тестового target пересобрать и его.
Host unit/type/syntax checks — вспомогательные. Финальное подтверждение поведения
должно относиться к новым контейнерам. Не использовать общую debug БД для
разрушительных тестов и не давать fake provider доступ к настоящим аккаунтам.

`git diff --check` и проверка затронутых файлов обязательны для плана/документации.
Тесты PGlite полезны для детерминированной логики, но не заменяют многосоединительные
гонки и lease tests PostgreSQL. Если Docker/health/нужная интеграция недоступны,
отметить конкретную проверку незавершённой.

## P9. Будущее выделение в сервис

Не выполнять в рамках первого MVP. Запускать при втором потребителе или явной
потребности в независимой эксплуатации. Пошаговый cutover и rollback описаны
в архитектурной спецификации. Критерий готовности к выносу: payments работает
через тот же контракт с отдельной тестовой БД и не импортирует продукт.
Критерий выполненного выноса: HTTP transport и сервисная аутентификация
проверены, IDs/dedup/outbox сохранены, один владелец записи, нет потерянных
оплат и повторных выдач, проверено восстановление после сбоя.
