## Главный вывод

Первое измеренное ограничение веба — конкуренция за соединения PostgreSQL.
Увеличение пула с 5 до 15 позволило выдержать 40 HTTP/с в коротких и
пятиминутных прогонах; чтение и приём задач также сокращены. Повторный
всплеск 25 mock-задач сохранил корректность денег, но предварительная цель
p95 POST ≤1 с на удалённой БД не достигнута. Пагинация, файлы, SSE и режим
одного executor с веб-репликами проверены отдельно; длительные и аварийные
прогоны определяют их эксплуатационные пределы.

Ниже покрыты все основные участки пути: браузер → HTTP/auth → БД/кошелёк →
очередь → провайдер → файлы → история/обновления, а также запуск и восстановление.
Полноту списка физических пределов нельзя доказать короткими тестами:
часть механизмов найдена в коде, но величина их влияния ещё не измерена.
Каждая такая запись имеет эксперимент, после которого её можно подтвердить
или снять с приоритета.

Сырые файлы игнорируются Git; `sessions.json` содержит cookie и не является
публичным доказательством. Полный паспорт конфигурации при каждом старом
прогоне отсутствует: например, размер пула очередного queue-прогона нельзя
надёжно восстановить только из его k6 JSON. При повторе записывать его явно.

`journalPeak10s=25` в queue4 не опровергает ограничитель: журнал и выдача
разрешения относятся к разным моментам. Отдельный `limiter-slots.json`
подтверждает максимум 20 разрешений за 10 секунд. При этом будущая проверка
должна измерять и фактическое начало HTTP POST: между разрешением и POST
сейчас есть операции с БД, способные сблизить отправки.

## 2. Реестр проблем и гипотез

Приоритет **P0** — нужен для достоверной диагностики или защиты результатов;
**P1** — исправить для роста одного экземпляра; **P2** — проверить после
основных причин. Приоритет зависит и от этапа: подготовка реплик обязательна
перед второй репликой, но не блокирует оптимизацию одного экземпляра.

### B01. Ожидание соединений PostgreSQL — P1, измерено

- **Доказательство:** ступени пула 5/10/15 выше; настройка в
  `src/database/database.js` и `src/server/config.js`, штатный пул 5.
- **Найти причину:** отдельно измерять ожидание `pool.connect`, время удержания
  клиента, выполнение SQL, ожидание блокировок и количество SQL на HTTP.
  Замер `SELECT 1` включает сеть и ожидание пула, поэтому его 56–87 мс
  нельзя объявлять чистой сетевой задержкой. Сопоставить с серверным временем SQL.
- **Исправление:** сначала убрать лишние запросы B02–B07, затем выбрать пул
  по повторным ступеням. 15 — кандидат для одиночного стенда, не новый default.
  Бюджет: сумма пулов веба, worker, фоновых клиентов и резерва должна помещаться
  в фактический лимит роли/прокси/сервера. `max_connections=100` не означает
  100 доступных этому приложению соединений. PgBouncer рассматривать после
  измерения стоимости соединений и проверки совместимости транзакций.
- **Приёмка:** на одной и той же нагрузке уменьшаются p95 ожидания и sync;
  очередь ожидающих не растёт, таймаутов получения соединений нет.

### B02. Полный workspace делает лишние обращения и блокирует аккаунт — P1, код

- `src/server/http.js` вызывает `ensureDefaultChat` при каждом полном sync;
  `src/services/workspaces.js` открывает транзакцию с `FOR UPDATE` аккаунта
  даже для существующего чата. Затем получает сведения о чате. История
  трёх провайдеров, проекты, чаты и курсор читаются отдельными запросами.
- **Проверка:** трасса одного холодного и прогретого sync; 1/5 вкладок одного
  аккаунта против такого же числа разных аккаунтов. Снять время блокировок.
- **Исправление:** быстрый путь чтения существующего основного чата; создание
  оставить атомарным при его отсутствии. Пакетировать данные там, где это
  сокращает обращения. Сохранить контракт курсора и delta, корректность
  параллельного создания/архивации чата; не подменять это кешем без инвалидации.
- **Приёмка:** обычный full sync не берёт блокировку аккаунта для существующего
  чата; две вкладки не создают дубликат; после записи во время sync нет потерянных изменений.

### B03. Медленное принятие генерации — P1, задержка измерена, причина требует трассы

- Путь: auth → `accounts.scope/assertBinding` → `media-service.createTask` →
  поиск requestId/настройки/тариф → `AccountRecords.update` → резерв/запись.
  POST возвращает сохранённую запись, не ждёт завершения генерации.
  Поэтому объяснять все 9,32 с только лимитом Kie нельзя; фоновые отправки
  могут конкурировать с приёмом за ту же БД.
- `nativeQuote(..., true)` обновляет каталог на границе платной отправки;
  `Tariffs` создаётся на аккаунт. Общий каталог может загружаться одновременно
  многими аккаунтами. Заглушка отдаёт одну страницу сразу, реальная сеть здесь не измерена.
- **Проверка:** времена каждого этапа; с указанным chatId и без него; тёплые
  и холодные аккаунты; 25 разных аккаунтов и 25 отправок одного аккаунта;
  реальный по структуре многостраничный тариф через локальный double.
- **Исправление:** адресный поиск requestId, пакетирование настроек, общий
  in-flight запрос публичного каталога с правильной областью данных. Сохранить
  проверку актуальной цены и атомарное резервирование до платной отправки.
- **Приёмка:** p95 принятия 25 задач ≤1 с как предварительная цель; один
  requestId даёт одну задачу/резерв, другой payload с тем же ID отклоняется.

### B04. Кошелёк блокируется для любого обновления записи — P1, код

- `src/database/records.js: AccountRecords.update` вызывает `lockWallet`
  для всех namespaces: history, preferences, drafts, sources и т. д.
  Обновления progress и черновика сериализуются с расчётом кредита одного
  аккаунта. `reserve/settle` дополнительно берут тот же lock в транзакции.
- **Проверка:** SQL/lock wait по namespace; одновременно вводить черновик,
  обновлять progress и создавать задачи одного аккаунта. Повторные lock-запросы
  уже удерживаемой строки учитывать как лишние round trips, а не новый deadlock.
- **Исправление:** отделить обновления без денежных операций; сохранить
  согласованный порядок wallet → record там, где меняются резервы/списания.
  Новая вставка и CAS должны остаться безопасными без общей блокировки кошелька.
- **Приёмка:** черновик/progress без расчёта не блокируют кошелёк; конкурентные
  reserve/capture/release сохраняют баланс, не списывают дважды и не допускают перерасхода.

### B05. Полное чтение истории и запрос на каждый файл — P1, код

- `AccountRecords.list()` без LIMIT; `generation-history.js` объединяет и
  сортирует всю историю. Очередь, поиск requestId и `getTask` тоже используют
  полные списки. `presentHistory` делает отдельный `content.get`, S3 HEAD
  или `stat` для каждого файла. Счётчики чатов/проектов используют подзапросы
  по JSON `chatId/projectId`; специальных индексов этих выражений в schema нет.
- **Проверка:** 0/100/1000/10000 синтетических записей на аккаунт, несколько
  файлов на запись; SQL, размер JSON, серверная память, DOM и время рендера.
  `EXPLAIN (ANALYZE, BUFFERS)` на тестовой БД покажет, нужны ли новые индексы.
- **Исправление:** адресные get/requestId; SQL только активных/готовых к запуску
  задач; пагинация истории; пакетное получение metadata файлов. Индексы добавлять
  по планам запросов. Не обходить проверку принадлежности файлов аккаунту.
- **Приёмка:** опрос 5 активных задач не читает 10000 завершённых; число SQL
  для страницы истории не растёт на каждый файл. Пагинация сохраняет доступ
  к старым материалам, курсор, активные задачи и позицию прокрутки.

### B06. Пустые очереди продолжают работать, сервисы аккаунтов не освобождаются — P1, код

- `TaskQueue.tick()` в finally снова планирует tick, пока очередь не paused,
  даже без задач; период по умолчанию 2 с. Каждый tick читает всю историю и
  вызывает notify. `createAccounts.services` хранит созданные сервисы без eviction.
  После хотя бы одного запуска аккаунт может продолжать фоновую работу до
  остановки/паузы. Само открытие пустого аккаунта ещё не запускает такой цикл.
- **Проверка:** 100/1000 аккаунтов по очереди выполняют одну mock-задачу и
  закрывают вкладки. Через 10 минут измерить SQL/с, таймеры, listeners, RSS.
- **Исправление:** спящая очередь без готовых/активных задач; пробуждение при
  enqueue, ближайшем retry, завершении и явном start. Срок жизни неактивного
  сервиса с безопасным закрытием таймеров; активные задания не выгружать.
- **Приёмка:** после опустошения нет регулярного сканирования истории и
  ложных changed; новая задача и отложенный retry гарантированно пробуждают очередь.

### B07. Повторные опросы и усиление событий — P1, код

- Backend Codex вызывает `status` каждые 1,5 с; браузер также опрашивает каждую
  активную задачу каждые 1,5 с, затем делает workspace sync. `status` может
  сохранять PNG, а общей защиты от одновременной финализации до транзакции нет.
  Kie опрашивается очередью примерно раз в 2 с; web обновляет sync раз в 2,5 с.
  `changed` дополнительно вызывает `refreshAccess`, то есть `/api/account`.
  В studio уже есть защита одного sync in flight — её нужно сохранить.
- **Проверка:** одна задача с 1/5/20 вкладками; число provider status, sync,
  SQL, загрузок PNG, созданных assets. Отдельно серия событий без изменения данных.
- **Исправление:** один владелец опроса/финализации и общий выполняющийся promise
  на задачу; браузеру отдавать сохранённый статус. Пакетировать/coalesce события,
  не обновлять права на каждый progress; polling оставить контролируемым fallback.
- **Приёмка:** число опросов провайдера не зависит от числа вкладок; результат
  сохраняется один раз, отключение SSE не оставляет UI без обновлений.

### B08. SSE ограничен 20 вкладками на весь процесс — P1, измерено

- `src/server/http.js` проверяет общий `connections.size >= 20`.
  Каждое соединение проверяет auth через БД каждые 15 с. EventSource
  автоматически переподключается после отказа, что тоже создаёт запросы.
- **Проверка:** 20/25/100/500 соединений, несколько вкладок одного пользователя,
  медленные читатели, массовый reconnect, logout и смена роли; RSS, sockets,
  SQL heartbeat и время доставки конечного состояния.
- **Исправление:** конфигурируемый общий бюджет и лимит на пользователя;
  разнесённые heartbeat/reconnect, защита от накопления буферов, явный fallback.
  Увеличивать бюджет после B06/B07 и оценки auth SQL. Проверку отзыва сессии сохранить.
- **Приёмка:** выбранное число вкладок получает обновления без неожиданных 429;
  logout закрывает доступ, медленный клиент не удерживает неограниченный буфер.

### B09. Последовательное сохранение контента и частый SQL wait — P1, код

- `content-service.tick()` выполняет один `processJob` за раз. Сохранение
  включает скачивание, PUT, HEAD и полное обратное чтение для SHA-256.
  `wait()` опрашивает строку БД с паузой 25 мс: верхняя оценка при очень быстрой
  БД — 40 запросов/с на ожидающий файл, реальная частота ниже из-за SQL latency.
  Эти затраты отсутствуют в queue double с пустым `resultUrls`.
- **Проверка:** синтетические изображения и видео разных размеров, 1/5/25
  одновременных сохранений; отдельные времена queue/download/PUT/verify/ready,
  SQL waits, staging disk и сетевой трафик. Медленный файл вместе с короткими.
- **Исправление:** ограниченная настраиваемая параллельность сохранения;
  уведомление о готовности и редкий контрольный опрос вместо 25 мс. При
  оптимизации проверки S3 сохранить гарантию длины и контрольной суммы;
  изменение этой гарантии — отдельное решение, не просто удаление GET.
- **Приёмка:** большой файл не блокирует все маленькие; SQL wait ограничен;
  повреждение/неполная запись обнаруживаются, retry сохраняет UUID asset.

### B10. PNG и очередь Codex удерживаются в памяти — P0 до длительных генераций, код

- `codex-worker.js` хранит `imageBase64` в Map; чистка завершённых записей
  происходит при запросах и по возрасту от создания >1 часа, не по байтовому
  бюджету. GET статуса возвращает job вместе с Base64. Пул ограничивает
  активные запуски, но его очередь в `codex-app-server-pool.js` не ограничена.
  На каждом рабочем запросе worker также сканирует всю Map для удаления старого.
- По историческому среднему PNG 1 086 497 байт при 1 результате/с Base64 за
  час — около 4,86 ГиБ без накладных расходов. Это расчёт риска, не измеренная утечка.
- **Проверка:** 60–120 минут синтетических завершений с размерами PNG как в
  отчёте; heap/RSS, bytes cache, очередь, GC, размер ответа status и период покоя.
- **Исправление:** постоянное сохранение результата и подтверждение получения;
  в status только metadata, байты отдельным путём; кеш с лимитом байтов и
  гарантией доступности ещё не сохранённых результатов. Очередь принимать
  устойчиво на диск/в БД с ясным состоянием принятия и ресурсным бюджетом.
- **Приёмка:** память выходит на плато; перезапуск не теряет принятый результат;
  ограничение кеша не превращает оплаченный успех в недоступный файл.

### B11. Лимиты провайдера и одновременные повторы — P1, частично измерено

- Исторический Codex 429 подтверждён; область лимита неизвестна. Kie limiter
  разрешает 20 отправок/10 с в одном процессе. Общий retry использует
  задержки 10→60 с без jitter; Kie ставит паузу 10 с. `Retry-After` в решение
  планировщика не передаётся. Нет общей политики максимального возраста ожидания.
- **Проверка:** double с 429 и разными Retry-After, длительными отказами,
  потерянным ответом после принятия; сверять время настоящего POST, FIFO,
  голодание аккаунтов, резервы, восстановление retry после рестарта.
- **Исправление:** нормализовать доказательство отказа и Retry-After,
  добавить разнесение повторов и метрики ожидания; регулировать отправку по
  измерениям общего аккаунта/ключа. Политику срока очереди/возврата резерва
  оформить явно. Не назначать 128 или 256 успешной эксплуатационной мощностью.
- **Приёмка:** unknown никогда не создаёт повторную платную отправку;
  подтверждённые отказы повторяются не раньше разрешённого срока; запросы
  одного аккаунта не вытесняют остальные. Реальные пределы измерить отдельно.

### B12. Память загрузок и синхронный журнал — P2, код; влияние не измерено

- HTTP собирает тело загрузки в память (штатный предел 64 МиБ); Codex worker
  допускает тело до 128 МиБ, JSON/Base64 создают дополнительные копии.
  `createFromBuffer` копирует Buffer. `generation-log.js` на каждой записи
  синхронно делает файловые операции и append/rotation в потоке Node.
- **Проверка:** параллельные загрузки разрешённых размеров, оборванные передачи,
  медленный диск и ротация; RSS/heap/external memory, event loop delay, p99 API.
- **Исправление:** потоковая загрузка со счётчиком байтов и ограничением
  одновременно обрабатываемого объёма; меньше копий; асинхронный журнал с
  ограниченной очередью и определённым поведением при её заполнении.
- **Приёмка:** RSS укладывается в бюджет, API остаётся доступен, незавершённые
  временные файлы удаляются; важные события учёта остаются в транзакционной БД.

### B13. Один executor и несколько веб-реплик — P0 перед масштабированием, код

- `service.lock` защищает общий каталог; локальные очереди/лимитер/events и
  worker Map не дают общей координации. CAS и уникальные индексы уже защищают
  часть операций, но восстановление в другом процессе не знает владельца.
  `payment_outbox.deliver` теперь использует атомарный claim, lease и токен
  подтверждения. Telegram polling запускается только у executor.
- У контента уже есть `FOR UPDATE SKIP LOCKED`, но staging привязан к workerId
  из локального каталога; восстановление processing идёт по этому ID. Этого
  недостаточно для падения узла и локального файла, недоступного другому узлу.
- **Проверка:** после проектирования владения — две реплики, один поток,
  падение владельца до/после POST и до/после списания; статус и SSE через
  другую реплику; повтор outbox, доступность staging, перезапуск worker.
- **Исправление:** выбран один executor с файловым и сеансовым PostgreSQL
  владением. Веб-реплики потоково пересылают записи и чтут общий каталог;
  LISTEN/NOTIFY доставляет события. Подробный [контракт](replica-ownership.md).
- **Приёмка:** две реплики, затем 5/10 при одинаковом общем трафике, без
  повторной отправки и списания. Сеансовый lock не должен допускать второго
  executor. Распределённое выполнение несколькими executor требует отдельного
  lease/fencing и общего limiter; выбранный режим ограничивает их число одним.

### B14. Генератор нагрузки ограничивает выводы — P0, измерения и код стенда

- `web.js` ограничен 10 циклами/с и числом сессий; `maxVUs=VUS`; содержит
  `sleep(1)` и пять последовательных HTTP. На 50 HTTP/с 25 VU недостаточно
  для хвоста задержек. Thresholds допускают почти 5% ошибок, не проверяют
  latency и dropped iterations; отсутствие cursor может молча пропустить delta.
- `queue.js` строит ID из `__VU/__ITER` при shared-iterations: распределение
  итераций по VU не обязано повториться. Для строгого replay нужен сохранённый
  список requestId/payload, а не только тот же RUN_ID. `verify.cjs` сверяет
  агрегаты; нужен ещё контроль каждой задачи/резерва/проводки отдельно.
- **Исправление стенда:** отдельные arrival-сценарии маршрутов и реальный
  пользовательский сценарий; достаточно заранее выделенных VU/аккаунтов;
  assertions на payload/cursor, thresholds на p95/ошибки/drops. Паспорт:
  commit + dirty diff hash, image digest, конфиг без секретов, fixtures, время,
  соседние контейнеры, ресурсы генератора и результаты по маршрутам.
- **Приёмка:** поток действительно отправлен; генератор имеет запас CPU/RAM;
  один и тот же список replay воспроизводится независимо от VU scheduling.
  Тест с намеренно плохим cursor/задержкой/дропами обязан провалить проверку.

### B15. Неизмеренные режимы и неполная наблюдаемость — P0 для диагноза

- Нет длинного смешанного теста, старых аккаунтов с большой историей,
  сквозного media save, UI/статики/исходников, длительного SSE под генерацией,
  массового reconnect и аварийного восстановления. Короткие выборки CPU
  ниже 5% не исключают паузы event loop, диск или сетевые ожидания.
- **Добавить:** времена этапов и SQL без параметров, route p50/p95/p99,
  accepted/success/rejected/unknown, oldest queue age, retry due lag, CPU/RSS,
  event loop/GC, bytes/cache/staging, pool wait/hold, DB locks/SQL, sockets,
  reconnect и актуальность последних данных UI. Без account/requestId как
  неограниченных labels метрик; связь запросов хранить в защищённых трассах.
- **Проверка сбоев:** недоступность/замедление БД, заполнение пула, ошибка S3,
  недоступный файл, restart web/worker, потеря ответа после принятия, logout
  и истечение сессии. Измерить накопление ожиданий и восстановление.
- **Исправление по результатам:** сквозной deadline, ограничение ожиданий и
  разнесение повторов. Сейчас получение соединения может повторяться, а
  отдельные чтения HTTP дополнительно повторяются; точную верхнюю задержку
  и нагрузку повторов нужно измерить, не складывать настройки на глаз.
- **Приёмка:** каждый отказ отнесён к этапу и сверяется с задачей/деньгами;
  после снятия нагрузки система возвращается к исходному уровню ресурсов.

Первый исполняемый пакет: **A + диагностика B01/B03/B06**. Он должен объяснить
9,32 с POST, стоимость одного sync и SQL после опустошения очередей.
Не начинать с массового увеличения пулов и количества веб-контейнеров.

### Матрица экспериментов

1. **Чтение:** контрольные старые 15/20/30/40/50 HTTP/с при пулах 5/10/15,
   одинаковые fixtures. Сначала 2 минуты прогрева, затем 5 минут ступень;
   возле границы три повтора с чередованием конфигураций. Успешный уровень
   подтвердить 30–60 минутами. Прекратить рост при нарушении выбранного SLO.
2. **История:** 0/100/1000/10000 записей; 1/5 файлов на запись; полный и
   добавочный sync отдельно, с изменениями во время чтения и без них.
3. **Очередь:** всплески 1/5/25 задач; отдельно один и разные аккаунты,
   chatId задан/не задан, warm/cold; ровный поток ниже и выше скорости double.
   Измерять очередь после окончания потока, не только ответы POST.
4. **Обновления:** 20/25/100/500 SSE и 1/5 вкладок на аккаунт, затем смешать
   с очередью. Числа — ступени исследования, не обещанная ёмкость.
5. **Контент:** файлы 1/10/64 МиБ и видео выбранного допустимого размера,
   1/5/25 сохранений, медленный источник/хранилище, повреждение и retry.
6. **Долгая работа:** 60–120 минут результатов double для памяти и 100/1000
   ранее активных аккаунтов для фоновых таймеров. После нагрузки 10 минут покоя.
7. **Сбои и реплики:** перечисленные B13/B15 точки отказа; сверить каждую
   задачу, asset, reserve/capture/release. Не перезапускать платный unknown.
8. **Целевой хостинг:** повторить выбранный профиль с его БД, storage,
   reverse proxy/TLS и лимитами ресурсов. Локальные показатели не переносить автоматически.

Новые ступени требуют расширить текущие ограничения стенда в пакете A;
их нельзя просто передать в существующие скрипты. Для длинного теста проверить
срок сессии: `prepare.cjs` выдаёт cookie на 2 часа, включая подготовку и прогрев.

### Предварительные критерии качества

Это предлагаемые инженерные цели для первого цикла, пока продуктовые SLO и
целевой трафик не заданы. Они не описывают уже достигнутую мощность.

- При входных 40 HTTP/с выбранной смеси: p95 full sync ≤1 с, delta ≤0,5 с,
  p99 full ≤2 с; принятие всплеска 25 mock-задач p95 ≤1 с.
- В прогоне без внесённых ошибок: HTTP failures <0,1%, checks=100%, drops=0;
  дубли отправок/списаний, потерянные принятые задачи и неожиданные unknown — 0.
- p95 ожидания соединения ≤100 мс; средняя длина очереди ожидания не растёт.
  SQL-время и lock wait фиксировать отдельно; если цель недостижима в данной
  сети/БД, указать конкретный расход времени и пересмотреть размещение.
- SSE: предварительно 100 вкладок, p95 доставки сохранённого конечного
  состояния ≤2 с; дополнительно время его появления в UI. Авторизация сохраняется.
- После прогрева нет устойчивого роста памяти сверх учтённых очередей/кеша;
  минимум 20% запаса до заданного лимита контейнера как стартовое правило.
- Для файлов и генераций задать разные SLO по размеру/модели до реального
  прогона. Универсальная секунда на готовое видео здесь не задаётся.
- Остановка ступени: нарушение целевого p95 два окна подряд, рост backlog,
  память ≥80% лимита, потеря наблюдаемости, любой дубль/потеря учёта. После
  остановки новых запросов дождаться уже принятых и выполнить сверку.

## 4. Правила исправления и проверки

Для каждого Bxx вести строку: статус → доказательство → причина → изменение
→ повтор того же сценария → эффект → остаточный риск. Сначала подтвердить
вклад механизма в задержку/ресурс, затем выбирать исправление; измерение
может снять гипотезу с приоритета. Сравнивать одинаковый входной поток,
данные и окружение, менять за опыт один фактор.

Сохранить: изоляцию аккаунтов; цену и резерв до платной отправки; атомарную
финализацию; безопасный unknown; CAS и уникальность requestId; восстановление
очереди; доступность сохранённых файлов; курсор и историю UI. Изменения
публичной пагинации, схемы хранения, политики retry/очереди и межрепличного
владения оформить отдельными контрактами перед внедрением.

После каждого пакета правок — обязательные `docker compose up -d --build`,
`docker compose ps` и `http://127.0.0.1:3000/api/health`, затем проверки
поведения на свежих контейнерах. Нагрузку выполнять на выделенном Compose
и БД по [runbook стенда](../tools/load-test/README.md), также пересобранных
из того же состояния. Рабочую БД не использовать как нагрузочную фикстуру.
Обязательная проверка основного Compose подтверждает runtime после правок,
но не доказывает улучшение производительности.

Итог исследования: по каждому сценарию указаны устойчивая интенсивность,
p95/p99, ошибки/unknown, очередь, ресурсы, ограничивающий этап и запас;
по каждой гипотезе есть измеренный результат или явный пробел. Реальные
провайдеры требуют отдельного бюджета; этот план его не назначает.

- Запас VU выбирать по длительности итерации и темпу; dropped iterations

  [node-postgres](https://node-postgres.com/guides/pool-sizing).
- Решение об индексах принимать по плану и фактическому выполнению на
  тестовых данных: [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html).
