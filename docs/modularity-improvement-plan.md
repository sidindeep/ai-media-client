## Цель и результат

Сделать границы модулей явными и проверяемыми: у каждого значимого модуля есть
ответственность, владелец данных, публичный интерфейс, разрешённые зависимости
и проверка рабочего сценария. Изменение одного провайдера или способа хранения
должно затрагивать его адаптер и потребителей его контракта в понятном объёме.

Работы выполняются в текущем модульном монолите, репозитории и Compose-проекте.
Рефакторинг сохраняет HTTP API, форматы записей, цены, права доступа, очереди и
пользовательские сценарии. Изменения этих контрактов оформляются отдельными
задачами с перечислением потребителей и порядком перехода.

Сквозной сценарий приёмки: пользователь открывает чат, сохраняет черновик и
исходник, получает цену, отправляет генерацию, видит результат и правильный
баланс после обновления страницы. Повтор запроса не создаёт вторую генерацию;
ошибка или неизвестный исход обрабатываются по действующему контракту провайдера.
Для внешней оплаты APIMart сохраняется собственная модель расчётов.

Начальное разбиение для проверки по коду:

| Область | Ответственность и данные | Публичные операции |
| --- | --- | --- |
| Доступ и аккаунты | Идентичности, сессии, роли, проверка владельца | Вход, получение пользователя, проверка доступа |
| Рабочие области | Проекты, чаты, черновики, пресеты | Выбор, сохранение, перенос, архивирование |

| Провайдеры | Перевод общего запроса в нативный протокол и обратно | Каталог, цена, статус, submit/getTask, загрузка по capability |
| Кредиты | Баланс, резерв, списание, возврат и конвертация | Котировка и атомарные денежные операции |
| Контент | Каталог файлов, доступ, загрузка, сохранение, фоновые задания | Сохранить, связать, прочитать, удалить по контракту |
| Commerce / Payments | Заказы и выдача покупки / денежный цикл провайдера | Checkout / PaymentClient и события |

Это рабочая схема границ. Конкретных владельцев общих записей и транзакций
закрепить после проверки кода. Для auth, конфигурации, ошибок, журналов,
идентификаторов и миграций указать общие правила и ответственные области.

**Приёмка:** каждое важное состояние имеет одного владельца; каждая связь
сослалась на публичный контракт или явно обозначенный общий read model.
Планируемые границы отделены от реализованных; все утверждения имеют ссылки на код/тесты.

## Проверки и порядок выпуска пакета

После завершения правок каждого пакета выполнить обязательную последовательность:

```powershell
docker compose up -d --build
docker compose ps
Invoke-RestMethod -Uri http://127.0.0.1:3000/api/health
```

Дождаться healthy у ожидаемых сервисов и `ok: true` у API. Далее выполнить
проверки затронутого поведения на свежем контейнере. Для M1 и M6, а также после
переноса общих границ использовать документированные наборы:

```powershell
docker compose --profile test run --build --rm tests
docker compose --profile test run --build --rm browser-tests
git diff --check
```

Health подтверждает готовность сервиса; результат сквозного сценария фиксируется
отдельно. Пробы оплачиваемых API не входят в обычный регрессионный набор.

Каждый пакет заканчивается списком изменённых контрактов и потребителей,
результатами проверок, обновлением памяти и следующим шагом. При регрессии
останавливается переход соответствующего маршрута; возврат выполняется scoped
откатом его кода с сохранением пользовательских данных и посторонних изменений.
Для изменения публичного контракта или схемы заранее нужен отдельный порядок
совместимости, наблюдения, отката и удаления прежнего пути.

## С чего начать

Первый пакет — M0 и инвентаризация покрытия из M1. Его результат: актуальная
карта, владельцы данных, перечень допустимых зависимостей и список недостающих
тестов. Следующий пакет — извлечение сборки провайдерских сервисов из HTTP с
проверкой старта и восстановления БД. После него переносить по одной группе маршрутов.
