# Диагностика и журнал генераций

## Технические логи — только ai_logger

По решению владельца от 2026-09-30 техническая диагностика отправляется только
по HTTP в ai_logger. `src/ai-logger/` содержит собственные копии общего Node.js
клиента, sanitizer и recorder. Внешний репозиторий не нужен при сборке и работе.

```dotenv
AI_LOGGER_SERVER_URL=https://ailogger.bothost.tech/ingest
AI_LOGGER_SERVICE=executor
AI_LOGGER_ENVIRONMENT=production
AI_LOGGER_ALLOW_PRIVATE_HTTP=0
```

Проект определяется автоматически как `ai-media-client`, экземпляр — по
фактическим hostname и PID процесса (в Docker это hostname контейнера). Эти поля
не нужно задавать на хостинге или локально. Пересозданный контейнер может иметь
новый instance_id; executor и web различаются фактическим hostname/PID и ролью
`AI_LOGGER_SERVICE`. Старые `AI_LOGGER_PROJECT` и `AI_LOGGER_INSTANCE_ID` из
окружения игнорируются: все реплики сами сообщают фактическую идентичность. Отправка,
HTTP-reader и проверка доставки используют единый resolver идентификаторов.
`.env` не коммитится и не входит в образ.

HTTP отправляет имя события и error_code без изменения, а также очищенные
`exception: { type, message, stack_trace }` и выбранные context-поля
`description`, `file`, `line`, `function`, `entity`. Исходный Error передаётся из
перехвата без создания нового Error; file/line/function извлекаются из его
первого кадра V8, стек ограничен 4000 символами, сообщение и описание — 1000.
Если исходного стека или места нет, эти данные не создаются. Сущность обозначает
тип компонента (task, provider, configuration и т. п.), без аккаунтных ID.
Пакетный forwarder принимает row.exception и row.diagnostic.

Перехват `console.error` сохраняет исходный `Error`, его код, стек и место
ошибки. Строковые аргументы проходят sanitizer и становятся `description`
(до 1000 символов); объекты и прочие payload-аргументы не сериализуются.
Строковое сообщение без `Error` получает описание, но не выдуманный exception
или стек. Обработчики HTTP, cleanup, повторной отправки и браузера передают
исходный `Error`, а не только его message/code.

Произвольные details, prompts, cookies, аккаунтные данные, тела запросов и сырые
ответы провайдеров не отправляются. Sanitizer удаляет зарегистрированные секреты,
Bearer/ключи, cookie, подписанные параметры URL, URL credentials, email и
маркированные prompts/account IDs; JSON в тексте ошибки скрывается как payload.
Разрешённые поля повторно очищаются HTTP-клиентом. Чистое техническое сообщение
ошибки остаётся доступным; не помещайте пользовательские данные в Error.message
без обозначения и очистки. Бизнес-журналы и обработка ошибок сохраняются.
События имеют уровни INFO/WARNING/ERROR.

Ответы Telegram API не создают регулярные `telegram.response` INFO-записи,
включая пустые ответы polling. Ошибки сохраняются как `telegram.error` с
методом и HTTP/API-кодом в очищенном сообщении; события запуска, остановки и
обработки входящих обновлений продолжают отправляться.

Успешные `chat.page.served`, `chat.history.loaded` и `chat.sync.loaded`
отправляются как INFO через отдельный адаптер `system-errors.info`; пользовательские
details не передаются. Строковые ошибки сохраняют очищенное описание без
выдуманного стека. Telegram API failures содержат method, HTTP/API code без
сырого ответа; штатная отмена polling при shutdown не считается ошибкой.
Ошибки HTTP Codex получают код `CODEX_HTTP_<status>`; 404 остаётся неизвестным
исходом с сохранённым резервом и без автоматической повторной отправки.
Worker публикует success/failed только после атомарной записи итогового статуса
на диск; изображения сохраняются до success. Перезапуск после опубликованного
успеха восстанавливает сохранённый результат без повторной генерации.

Пул БД освобождает простаивающие подключения через 30 секунд и включает TCP
keepalive с начальной задержкой 10 секунд. Выделенное LISTEN-подключение выполняет
`SELECT 1` каждые 30 секунд с timeout 5 секунд; при потере связи уничтожает
подключение и восстанавливает подписку с backoff 1–30 секунд. SQL-записи и
платные операции автоматически не повторяются. Эти меры не устраняют сбои
сети или сервера общей БД; повторные обрывы требуют дальнейшей диагностики.

Хранилище центра — `ai_logger_records`; `/api/agent/logs` возвращает записи по
project, levels, since и limit. На сервере также включён плагин daily JSONL.
Отдельная таблица `ai_logger_system_errors` этим HTTP-контрактом не заполняется.
Приложение не получает доступ к PostgreSQL логгера.

Чтение агентом:

```powershell
docker compose exec -T media node scripts/read-central-errors.cjs 50
Invoke-RestMethod -Uri 'https://ailogger.bothost.tech/api/agent/logs?project=ai-media-client&levels=ERROR,WARNING&limit=100'
```

`AI_LOGGER_READ_URL` выбирает альтернативный HTTP-reader; необязательный
`AI_LOGGER_READ_TOKEN` передаётся в Authorization. Текущий API открыт, поэтому
отправляются только очищенные поля диагностики.

Очередь ограничена 100 записями, повтор доставки — через 5 секунд, HTTP timeout —
1,5 секунды. Старейшая ожидающая запись удаляется при переполнении; отправляемая
строка защищена. Shutdown выполняет ограниченный drain и останавливает retry.
Недоставленные записи существуют только в памяти; после остановки процесса
теряются. Неоднозначный ответ может дать дубли при повторе. Сбой логгера не
должен ломать сервер, Telegram или генерацию. По умолчанию JSONL fallback отключён; существующий AI_LOGGER_FALLBACK_JSONL_PATH поддерживается клиентом и не удаляется.

## История прежней диагностики (до этого обновления)

Миграция `0021-central-diagnostics-only.sql` удаляет таблицу
`media_system_errors` вместе со старыми диагностическими строками по явному
запросу владельца. Исторические миграции сохраняются ради checksum. Приложение
больше не пишет в эту таблицу; SQL-reader удалён. Локальный `generation.jsonl`
и его ротация были отключены предыдущим изменением. Это обновление не удаляет
таблицы и старые файлы, не добавляет миграций; существующая история задач сохраняется.
После схемы v21 запуск приложения с миграциями только до v20 несовместим:
на всех площадках требуется новая версия исходников.

## Критичные этапы

При старте пишутся start/success/error для конфигурации runtime, каталога данных,
провайдеров, объектного хранилища, media-service, БД и конфигурации моделей,
контента/аккаунтов, восстановления генераций и платежей, HTTP listen и Telegram.
Ошибки до подключения БД также отправляются, так как клиент логгера подключается
первым. Uncaught exception, unhandled rejection и ошибки завершения получают
отдельные события перед попыткой отправки и завершением процесса с ошибкой.

Во время работы диагностируются API/провайдеры, сетевые запросы и retry,
потеря соединения БД, LISTEN/NOTIFY, очередь и сохранение результатов,
content worker/S3, платёжные операции, Telegram polling и обработка сообщений.
`record()` и `flush()` сохранены; `system-errors.step()` логирует этап и повторно
выбрасывает исходную ошибку. Платные отправки автоматически не повторяются.

## Пользовательские данные

Бизнес-журнал генераций в `media_records` (namespace `generation-journal`),
история задач, `errorInfo`, пользовательские сообщения и журнал расходов
сохраняются. Он учитывает созданные генерации и реальные попытки отправки,
привязан к аккаунту и доступен через `getGenerationJournal` с проверкой роли.
Удаление технической диагностики не удаляет задачи, исходники или результаты.

Проверки: тесты ai-logger, system-errors, generation-log, generation-journal,
provider-diagnostics, routerai, database-migrations; startup/health и безопасный
HTTP roundtrip на свежих контейнерах. Только состояние панели хостинга не
подтверждает доставку: событие должно быть принято и прочитано через API.

## Проверка подробной диагностики

Codex worker отправляет исходные ошибки выполнения и сохранения как
`codex-worker.run.error` и `codex-worker.persist.error` с ролью `codex-worker`.
Compose передаёт ему только настройки ai_logger; Dockerfile включает общий
адаптер `system-errors`. Код провайдера сохраняется в истории задания.
Ошибки внутренних повторов Codex учитываются только при итоговом отказе без
собственной причины; успешный результат остаётся успешным. Финальное пояснение
модели при пустом отказе изображения показывается владельцу с подписью
«Ответ модели» и не отправляется в центральный журнал. Стек и причина старых
отказов задним числом не восстанавливаются.

`docker compose exec -T media node scripts/verify-central-diagnostics.cjs` отправляет
безопасный Error с UUID-маркером и читает его через `/api/agent/logs`. Проверяет
исходный стек, русское описание, file/line/function/entity, ID машины и роль,
а также отсутствие тестовых приватных details. Для web-реплики команда та же
с сервисом `media-web`. Проверка не запускает генерацию и не меняет таблицы.

Охват: запуск/config, исходные ошибки шагов prepare/create/poll/complete очереди,
RouterAI/APIMart/Codex до преобразования в состояние задачи, HTTP/network,
DB/LISTEN, S3/content, платежи/Telegram, uncaughtException/unhandledRejection
и shutdown. Недоступность logger удерживает ограниченную retry-очередь;
существующие коды выхода и завершение процесса не меняются.
