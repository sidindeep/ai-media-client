# Web frontend: API и поведение генерации

Статус: зафиксировано 2026-09-19 перед переносом web-интерфейса на Vue 3 + Vite + Pinia + TypeScript.

Цель документа — сохранить наблюдаемое поведение текущего web-клиента при замене DOM-слоя. Backend, PostgreSQL, очередь и провайдеры в рамках миграции не меняются.

Новый Vue-клиент является основным web-интерфейсом на `/`. Совместимый адрес `/app` сохранён для старых ссылок, прежняя DOM-студия доступна только на `/legacy`. В шапке Vue-клиента отображаются канал, версия, дата/время Docker-сборки и build из `/api/version`.

## Границы клиента

Web-клиент работает в авторизованном account-scoped режиме. Для API-запросов передаются:

- `X-Media-Client: web` для операций записи;
- `X-Media-User: <текущий account id>`;
- администратор может передать `X-Media-Account: <account id>` или `?account=<account id>` для выбранного аккаунта.

HTTP-ошибка `401` переводит пользователя на `/login`. Ошибки записи не повторяются автоматически. Если результат платной отправки неизвестен, интерфейс должен сначала перечитать историю/статус, а не отправлять запрос повторно.

## Неблокирующий запуск

HTTP-сервер и Vue-оболочка запускаются до готовности PostgreSQL. Сервер параллельно выполняет два независимых read-only процесса: подключает account-БД с ограниченной задержкой между повторами и проверяет конфигурацию, авторизацию, тарифы и стартовую модель Kie без запуска генерации. Провайдерная проверка не открывает диагностическое окно и не блокирует подключение аккаунта.

Пока БД недоступна, `/` и `/app` возвращают обычную Vue-оболочку без account-данных. Клиент показывает неблокирующий спиннер «Подключаемся к базе данных…», раз в секунду читает `/api/startup` и оставляет остальной интерфейс видимым, но недоступным для операций. Account API, черновики и платные запросы до успешной проверки сессии отвечают `503`; заголовок аккаунта устанавливается только из подтверждённого startup-ответа. После восстановления БД клиент без перезагрузки загружает каталог, историю, проекты, чаты и черновик. Неудача проверки Kie не мешает восстановлению account UI.

## Общие HTTP-эндпоинты

| Метод | Эндпоинт | Назначение | Форма ответа |
| --- | --- | --- | --- |
| `GET` | `/api/startup` | безопасный статус фонового подключения БД, проверки Kie и подтверждённого account-контекста | `{ database, provider, authenticated, account }` |
| `GET` | `/api/health` | состояние сервиса, БД, генерации и Telegram | `{ ok, version, build, database, generationConfigured, telegram }` |
| `GET` | `/api/version` | версия и build | объект release |
| `GET` | `/api/account` | текущий аккаунт, identities и wallet | `{ result: ... }` |
| `POST` | `/api/rpc/:method` | account-scoped методы приложения | `{ result: value }` |
| `POST` | `/api/source?name=...` | загрузка исходника | `{ result: { ref, ... } }` |
| `GET` | `/api/sources/:sha256` | защищённое чтение исходника | бинарный файл |
| `GET` | `/api/results/:recordId/:index` | просмотр/скачивание сохранённого результата | бинарный файл |
| `GET` | `/api/events` | SSE-уведомления об изменении очереди/истории | `ready`, затем `changed` |

Для JSON-RPC тело — массив аргументов, максимум 5 аргументов и 4 MiB. Сервер возвращает `result: null`, если значение метода отсутствует.

## RPC-контракт текущего media-потока

Список методов, который должен быть доступен новому frontend API-клиенту:

| Метод | Аргументы | Поведение |
| --- | --- | --- |
| `getCatalog` | нет | каталог провайдера, моделей, полей и `inputSchema`; схема каталога является источником правды для формы |
| `getHistory` | нет | история media и Codex, отсортированная от новых к старым |
| `createTask` | `{ modelId, input, sourceFiles?, workspace?, requestId? }` | валидирует вход, выполняет дедупликацию и добавляет запись в локальную очередь |
| `getTask` | `providerId, taskId` | возвращает одну задачу или ошибку «Задача не найдена» |
| `queueStatus` | нет | `{ paused, error, concurrency }` |
| `startQueue` / `pauseQueue` | нет | запускает/приостанавливает новые отправки; активные provider-задачи продолжают опрашиваться |
| `setConcurrency` | число 1–5 | меняет лимит параллельных отправок и сохраняет настройку |
| `cancelQueued` | `recordId` | отменяет ожидающую задачу |
| `removeQueued` | `recordId` | скрывает задачу из очереди, история сохраняется |
| `clearQueue` | нет | очищает видимую очередь |
| `acknowledgeTask` | `recordId` | подтверждает задачу с неопределённым исходом |
| `getFavoriteModels` / `setFavoriteModels` | список id для записи | читает/сохраняет избранные модели |
| `listTemplates` / `saveTemplate` / `removeTemplate` | данные шаблона | операции с шаблонами промптов |
| `loadDrafts` / `saveDrafts` | draft v1 | общий workspace-черновик; текущая форма допускает 1–5 вкладок |
| `getBalance` | нет | баланс аккаунта |
| `diagnoseProvider` | `{ modelId, input }` | read-only проверка серверного ключа Kie, авторизации через баланс, живого тарифного каталога и цены модели; генерацию не запускает и секреты не возвращает |
| `saveResults` | `recordId` | скачивает внешние result URL в хранилище сервиса |

Для обычного account-scoped пользователя `createTask` требует `requestId`. Он должен быть UUID и использоваться для идемпотентности. Повтор с тем же ID и другим содержимым отклоняется.

## Генерация через media/Kie

Провайдеры Codex CLI и Kie.ai выбираются отдельным переключателем; список моделей содержит только модели выбранного провайдера. Имя Kie.ai приходит из `getCatalog`, а не зашивается во frontend. При смене media-модели форма удаляет поля, отсутствующие в новой схеме, и не отправляет параметры предыдущей модели.

1. Клиент получает каталог через `getCatalog` и строит форму по `fields`/`inputSchema`. Числа, boolean и JSON преобразуются в типы схемы до расчёта цены и отправки.
2. Перед отправкой собирает `modelId`, динамический `input`, список `sourceFiles`, номер `workspace` и новый `requestId`.
3. `createTask` сначала валидирует модель и поля, затем создаёт запись со `state=queued`.
4. Очередь обрабатывает задачу FIFO. Основные состояния: `queued → preparing → submitting → waiting/queuing/generating → success|fail`.
5. При `success` результат доступен через `resultJson` и `localFiles`; скачивание после успеха не занимает слот очереди.
6. При `unknown` повторная платная отправка запрещена. Пользователь должен проверить статус/историю и явно подтвердить результат.
7. SSE `changed` является сигналом перечитать `queueStatus` и `getHistory`; SSE не содержит саму задачу и не заменяет GET/RPC.

Ошибки подготовки получают `blocked`, отменённые ожидающие задачи — `cancelled`. При закрытии вкладки очередь на сервере продолжает работу.

В Kie-режиме доступна кнопка «Проверить Kie». Она открывает модальное окно с
результатами каждого read-only шага, описанием механизма запросов и последними
account-scoped записями расчёта. Значение `KIE_API_KEY`, баланс и сырые ответы
провайдера в браузер не передаются. Ошибка цены сопровождается кнопкой «Детали». Для `nativeQuote` и
`diagnoseProvider` сервер ограниченно повторяет временно оборвавшиеся чтения сессии и account-контекста, включая PostgreSQL
SQLSTATE класса `08`; платные и изменяющие состояние RPC этим механизмом не повторяются. Если первый read-only расчёт всё же
завершился общей временной ошибкой HTTP или подключения к БД, клиент один раз повторяет только этот безопасный расчёт.
`nativeQuote` маршрутизируется через общий media-service одинаково для пользовательского и административного аккаунта;
диагностика не должна быть необходима для первоначального получения цены или маскировать отсутствующий RPC-маршрут.
После изменения текста промпта media-расчёт запускается
через 1,5 секунды без новых изменений. С момента изменения до получения актуальной цены кнопка генерации заблокирована,
показывает спиннер и состояние «Расчёт…»; старая цена и старая ошибка сразу снимаются. Если обе попытки не прошли или
предыдущий расчёт формы завершился ошибкой, но диагностика для той же модели прошла все шаги и вернула цену,
её quote становится актуальным quote формы: старая ошибка снимается, а кнопка генерации разблокируется. Ответ для другой уже
выбранной модели форму не меняет.

Неожиданные server-side ошибки account API остаются скрытыми от браузера, но записываются в серверный журнал как
`service.request.error` с методом, путём, RPC и очищенным объектом ошибки. Тело запроса, ключи и cookie в такую запись не входят.

## Генерация через Codex

Отдельный HTTP-контракт используется для Codex CLI:

| Метод | Эндпоинт | Тело/параметры | Результат |
| --- | --- | --- | --- |
| `GET` | `/api/codex/status` | нет | `{ enabled, allowed }` |
| `GET` | `/api/codex/quote` | `model`, `effort`, `speed` | `{ quote, error? }` |
| `POST` | `/api/codex/jobs` | `prompt`, `model`, `effort`, `speed`, `requestId`, `kind?`, `aspectRatio?`, `sourceFiles?` | запись задания |
| `GET` | `/api/codex/jobs/:id` | нет | текущее состояние задания |
| `GET` | `/api/codex/jobs/:id/image` | `?download=1` для скачивания | PNG для успешной image-задачи |

Допустимые значения проверяются сервером:

- `prompt`: непустая строка до 20 000 символов;
- `speed`: `standard` или `fast`;
- `kind`: `text` или `image`;
- `aspectRatio`: `auto`, `1:1`, `16:9`, `9:16`, `3:2`, `2:3`;
- до 10 исходных изображений.

Перед `POST /api/codex/jobs` клиент получает quote. Кнопка запуска заблокирована, пока каталог не загружен, quote не получен или уже есть pending job. После неоднозначного ответа ID pending-запроса сохраняется, автоматический повтор запрещён. Для изображения результат появляется после `success` и отдаётся отдельным PNG-эндпоинтом.

SSE `/api/events` сообщает об изменениях media-очереди, но не является источником обновлений Codex. Пока в account-scoped истории есть Codex-задачи со статусом `submitting`, `running` или `generating`, Vue-клиент раз в 1,5 секунды выполняет только `GET /api/codex/jobs/:id`, затем перечитывает историю. Поллинг не создаёт задачу повторно, не списывает кредиты и прекращается после перехода всех Codex-задач в конечное состояние. Во время активной задачи интерфейс рассчитывает прошедшее время от `generationStartedAt`/`createdAt`, после завершения показывает сохранённый `generationDurationMs`.

## Состояние, которое должен сохранить Vue-слой

Минимальные Pinia-store:

- `session`: account, role, баланс, health;
- `catalog`: provider/model catalog, selected model и динамические поля;
- `generation`: prompt, attachments, settings, quote, pending request;
- `queue`: status, concurrency, active/queued records;
- `history`: completed/failed records и выбранный результат;
- `drafts`: текущий workspace и pending local snapshot;
- `templates`: шаблоны и избранные модели.

Переход к чатам и проектам добавляет необязательные `activeProjectId` и `activeChatId` в payload генерации, запроса Codex, сохранения исходника и черновика. Отсутствие этих полей означает системный workspace; сервер проверяет account scope и архивный статус до резервирования задачи.

## Критерии сохранения поведения при миграции

- текущая форма генерирует те же payload и использует те же endpoint/статусы;
- повторная отправка с тем же `requestId` не создаёт вторую платную задачу;
- `unknown` не превращается в автоматический retry;
- SSE только инвалидирует/обновляет Pinia-состояние;
- активная Codex-задача обновляется адресным GET-поллингом и появляется в UI без перезагрузки страницы;
- источники и результаты остаются account-scoped и не раскрывают серверные пути;
- черновик восстанавливается после перезагрузки;
- ошибки `401`, `403`, `409`, `503` показываются пользователю без потери pending ID;
- существующие `pnpm check`, web-тесты и UI smoke остаются зелёными.
