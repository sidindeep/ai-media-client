# План production CDN и Storage

Статус: обязательный план перед production-развёртыванием. Локальный debug-бакет
не изменяется этим документом. Необратимые настройки включаются только при
подготовке production-инфраструктуры и после фиксации сроков хранения.

## Цель и гарантия продукта

Оплаченный пользовательский контент хранится до явного удаления пользователем
или до предусмотренного договором/законом окончания хранения. Ошибка приложения,
компрометация рабочего ключа, удаление записи из чата, сбой диска или одного
облачного аккаунта не должны приводить к необратимой потере файла.

CDN ускоряет выдачу, но не становится источником истины. Источник истины —
каталог PostgreSQL и приватное объектное хранилище; восстановление требует обеих
частей.

## Зафиксированное исходное состояние

Read-only проверка 2026-09-22 определила текущий endpoint как Timeweb Cloud S3.
Провайдер заявляет тройную внутреннюю репликацию, но на текущем бакете:

- Versioning не включён;
- Object Lock не включён;
- Lifecycle отсутствует;
- независимая backup-реплика не настроена.

Тройная репликация защищает от аппаратного отказа внутри провайдера, но не от
корректно авторизованного удаления, ошибки приложения или компрометации ключа.
Текущий бакет не является эталоном production-защиты.

## Целевая архитектура

### Основное хранилище

- Отдельный приватный production-бакет, созданный с Versioning и Object Lock с
  самого начала. Публичный доступ к бакету полностью запрещён.
- Неизменяемые ключи `accounts/<account-id>/content/<asset-uuid>`: новый файл и
  перегенерация всегда получают новый UUID; существующий объект не
  перезаписывается.
- Текущие версии не удаляются Lifecycle автоматически. Перевод старых объектов
  в более дешёвый storage class допустим только после проверки поддержки byte
  ranges и приемлемого времени восстановления.
- Рекомендуемый начальный Object Lock — `COMPLIANCE` на 90 дней. Точный срок
  должен быть согласован с офертой, политикой удаления аккаунта и требованиями
  к персональным данным до запуска production. `LEGAL HOLD` применяется только
  для отдельных юридически значимых случаев, не ко всему пользовательскому
  контенту бессрочно.
- В PostgreSQL дополнительно фиксируются S3 `version_id`, размер и SHA-256.
  Чтение и восстановление должны уметь обратиться к конкретной версии.
- Перед переводом asset в `ready` подтверждаются HEAD, размер и полный SHA-256
  загруженного объекта.

### Разделение полномочий

Рабочий ключ приложения получает только минимально необходимые операции записи,
чтения, HEAD и ограниченного LIST на content-префикс. Ему запрещены:

- `DeleteObject` и `DeleteObjectVersion`;
- изменение Versioning, Object Lock, Lifecycle, bucket policy и репликации;
- `BypassGovernanceRetention`;
- удаление бакета.

Административный break-glass-доступ хранится отдельно от runtime и требует MFA.
CDN, backup-процесс и аудит используют разные учётные данные. Компрометация
приложения не должна давать возможность изменить политику хранения или удалить
резервную копию.

### CDN

- CDN читает только из приватного origin через отдельную origin identity/роль;
  прямой публичный URL S3 не используется.
- Приложение сначала проверяет tenant-владельца в PostgreSQL, затем выдаёт
  короткоживущий подписанный CDN URL или cookie. Рекомендуемый TTL — 5–15 минут.
- UUID-пути неизменяемы, поэтому CDN может долго кэшировать байты по пути после
  успешной edge-авторизации. Подпись и пользовательские query-параметры не должны
  создавать публично переиспользуемый обход авторизации.
- Сохраняются byte ranges для видео, корректные `Content-Type`,
  `Content-Disposition`, ETag и защита от MIME sniffing.
- CDN purge очищает только кэш и никогда не удаляет origin-объект.
- Provider URL, локальные пути и presigned S3 URL не становятся постоянными
  ссылками в истории или БД.

### Независимая резервная копия

Применяется схема 3-2-1: рабочая копия, версия/реплика и отдельная неизменяемая
копия в другом аккаунте, а предпочтительно — у другого S3-провайдера.

- Backup-бакет имеет собственные Versioning и Object Lock.
- Удаления и delete markers из основного бакета в backup автоматически не
  распространяются.
- Runtime приложения не имеет ключей удаления или администрирования backup.
- Копируются объекты, PostgreSQL backup и подписанный манифест
  `asset UUID → account → storage key/version → size → SHA-256`.
- PostgreSQL получает point-in-time recovery. Начальная цель: RPO не более
  15 минут, RTO не более 4 часов; значения подтверждаются нагрузочными и
  восстановительными испытаниями.
- Сроки хранения backup и Object Lock согласуются с политикой удаления данных.
  Запрос пользователя на удаление проходит отдельный аудируемый workflow и не
  обходится ручным удалением одного объекта.

## Удаление и восстановление

- Удаление сообщения, чата или генерации не удаляет asset физически.
- Пользовательское удаление сначала создаёт tombstone и карантин минимум на
  согласованный grace period; физическая очистка выполняется отдельной очередью
  только после истечения Object Lock и retention policy.
- Любое физическое удаление идемпотентно, журналируется и проверяет отсутствие
  живых `content_links`.
- Случайное удаление восстанавливается из конкретной S3-версии; потеря основного
  бакета — из независимого backup вместе с каталогом PostgreSQL.
- Документированный runbook восстановления содержит владельца операции,
  контрольные суммы, порядок возврата БД и объектов и проверку tenant-доступа.

## Мониторинг и доказательство сохранности

- Ежедневная сверка PostgreSQL ↔ основной S3 ↔ backup: отсутствующие объекты,
  размер, version ID, задержка репликации и S3-сироты.
- Непрерывные алерты на отключение Versioning/Object Lock, изменение bucket
  policy, появление delete API в runtime-роли и ошибки backup.
- Еженедельная выборочная проверка SHA-256; полный обход выполняется по графику,
  который не создаёт неприемлемую стоимость и нагрузку.
- Ежемесячное тестовое восстановление случайной tenant-выборки, ежеквартальное
  disaster-recovery упражнение с восстановлением PostgreSQL и S3 в чистое
  окружение.
- Метрики: RPO/RTO, возраст последнего успешного backup, число `missing`,
  `readyAbsent`, checksum mismatch, объекты без каталога и каталог без объекта.

## Этапы production-развёртывания

- [ ] Утвердить retention/grace period, правила удаления аккаунта, RPO/RTO и
  юридическую политику хранения.
- [ ] Создать новый приватный production-бакет с Versioning и Object Lock;
  проверить невозможность преждевременного удаления тестовой версии.
- [ ] Создать минимальную runtime-роль и отдельные admin, CDN, audit и backup
  роли; проверить запрет Delete и изменения bucket configuration.
- [ ] Добавить хранение `version_id` и startup/health guard: production не
  принимает генерации, если обязательная защита бакета отключена.
- [ ] Развернуть независимый immutable backup и PostgreSQL PITR.
- [ ] Настроить приватный CDN origin, короткие подписанные URL и range-smoke для
  изображений и видео двух разных аккаунтов.
- [ ] Перенести assets с проверкой размера/SHA-256, выполнить повторный аудит и
  только затем переключить чтение на production origin/CDN.
- [ ] Провести восстановление удалённого тестового объекта, всей тестовой учётной
  записи и согласованного снимка БД+S3.
- [ ] Включить алерты, регулярный аудит и календарь restore drills.
- [ ] После периода наблюдения запретить legacy-запись и оставить старое
  хранилище read-only до отдельного подтверждения очистки.

## Критерии допуска production

- runtime-ключ технически не может удалить объект или ослабить retention;
- известный UUID другого tenant не даёт доступ ни через приложение, ни через CDN;
- удаление current object создаёт восстанавливаемое состояние, а защищённая
  версия остаётся неизменяемой;
- потеря основного бакета и потеря рабочей БД отработаны на тестовом
  восстановлении в пределах RPO/RTO;
- audit не показывает `readyAbsent`, checksum mismatch и незащищённые assets;
- backup существует в независимом security boundary и его свежесть наблюдается;
- политика удаления пользователя реализована без обещаний «вечного» хранения,
  противоречащих закону или договору;
- инструкция восстановления проверена не только чтением, но и фактическим drill.

## Нормативная основа решений

Используются распространённые практики S3 Versioning, WORM/Object Lock,
least privilege, MFA/break-glass, независимые security boundaries, схема 3-2-1,
измеримые RPO/RTO и регулярная проверка восстановления. Внутренняя репликация
облачного провайдера не считается самостоятельным backup.
