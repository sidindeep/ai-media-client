# План замеров нагрузки и масштабирования

Статус: план, 2026-09-25. Число устойчивых CCU для веба и число устойчивых
генераций в минуту для Kie и Codex пока не установлены. Этот документ задаёт
порядок измерений и условия, при которых можно выбирать размер хоста и число
реплик. [План подробного теста Codex](codex-load-test-plan.md) и
[результаты коротких волн](codex-capacity.md) остаются источниками деталей.

## Что именно считать

| Показатель | Определение |
| --- | --- |
| CCU сайта | Пользователи, одновременно выполняющие заданный сценарий; отдельно считать открытые вкладки с SSE. Число зарегистрированных аккаунтов сюда не входит. |
| Интенсивность генераций | Новые задания и успешные результаты в минуту, отдельно по Kie и Codex, типу результата, модели и аккаунту провайдера. |
| Параллельность | Число заданий, реально выполняемых у провайдера; отдельно от ожидающих в очереди и пользователей в кабинете. |
| Рабочая мощность | Темп, выдержанный длительным прогоном с приемлемыми задержками, расходом памяти, ошибками и опустошением очереди после окончания потока. Короткая успешная волна не устанавливает рабочую мощность. |

Для расчёта активных пользователей указать поведение: если один пользователь
отправляет запрос каждые `T` секунд, оценка равна устойчивым результатам/с × `T`.
Показать также всплеск одновременных отправок: средний темп его не заменяет.

## Известная отправная точка и ограничения

- Локальный Compose сейчас запускает по одному `media`, `codex` и `kie-browser`.
  На хостинге одиночный образ запускает Codex и браузер Kie внутри веб-контейнера.
- Десять веб-реплик, направленных в один Codex worker, делят его пул и лимиты
  одного аккаунта. Настройка пула `2 × 128` задаёт число слотов, а не успешную
  производительность. Несколько worker с тем же аккаунтом также не гарантируют
  кратного прироста: ограничение провайдера может быть общим.
- На локальной Docker VM (12 CPU, 15,57 ГиБ RAM) короткая волна 128 PNG
  завершилась полностью: GPT-5.6 Sol — 128/128 за 75,73 с, GPT-5.5 — 128/128
  за 62,19 с. Волны 256 для GPT-5.5 дали массовые отказы; диагностика выявила
  `429 Too Many Requests`. Длительный прогон, полный веб-путь и хостинг не
  проверены. Нельзя считать 128 эксплуатационным пределом или гарантией.
- Генерации Kie используют серверные `KIE_API_KEY` / `KIE_API_KEY_2`.
  Администраторский браузер кабинета Kie хранит отдельную сессию и не участвует
  в обычной отправке генераций. Один браузер может оставаться постоянным
  сервисом при масштабировании веба.
- Сейчас `service.lock` запрещает два веб-процесса с общим каталогом данных.
  Очереди Kie и ограничитель `20 POST за 10 секунд` на ключ находятся в памяти
  процесса; с несколькими процессами это не единая очередь и не общий лимит.
  Предел `/api/events` — 20 SSE-подключений на веб-процесс. Сессии пользователей
  хранятся в PostgreSQL, но этого недостаточно для готовности к репликам.

## Порядок работ

### 1. Зафиксировать сценарии, окружение и бюджет

1. Выбрать целевой тип хоста и конфигурацию: CPU/RAM, лимиты контейнеров,
   PostgreSQL, хранилище файлов, сеть, версии образов, модель и аккаунт
   провайдера. Локальный Compose и хостинг измерять отдельно.
2. Утвердить профиль нагрузки: доли пользователей без генерации, Kie
   image/video, Codex image/text; запросов на активного пользователя в час;
   средний размер исходников/результатов; число вкладок на пользователя.
3. Задать до запуска целевые p95 для API и генераций, допустимую долю ошибок,
   бюджет платных запросов и предельную длительность очереди. Без этих целей
   результат нельзя назвать «достаточной мощностью».
4. Использовать отдельные тестовые аккаунты и баланс. Не включать реальные
   секреты, cookie, промпты и содержимое файлов в отчёты. Не повторять
   задания с неизвестным исходом автоматически.

Выход: паспорт прогона с версиями, топологией, входным трафиком, бюджетом,
целями и правилами остановки. Сырые данные хранить в `artifacts/load-tests/`
вне Git; сюда переносить только сводку и ссылки на доказательства.

### 2. Добавить наблюдаемость до роста нагрузки

- Собирать для каждого сценария: отправлено/принято/успешно/отказ/unknown,
  RPS, p50/p95/p99 от действия пользователя до результата, время в очереди,
  глубину очереди, число активных задач, `429` и `Retry-After` по провайдеру.
- Снимать CPU, RSS/heap и общую память контейнеров, число процессов и
  соединений, рестарты/OOM, задержку event loop, состояние PostgreSQL и его
  пула, объём локального/S3-хранилища и частоту опросов.
- Для Codex учитывать один серверный аккаунт, все worker и расход лимитов;
  для Kie — ключ/слот. На дашборде различать ошибку провайдера, ошибку нашего
  API и потерю наблюдения клиентом. Проверить, что счётчики сверяются с
  сохранёнными заданиями и кредитными резервами.

Выход: воспроизводимый отчёт без секретов и проверенный сбор метрик. Без
наблюдения за потерянными и неопределёнными исходами платные ступени не начинать.

### 3. Измерить текущий один веб-инстанс без платных генераций

Прогнать отдельно чтение лендинга/статики, вход уже авторизованного тестового
пользователя, открытие студии, историю/кошелёк, `/api/workspace/sync` и
длительные подключения `/api/events`. Провести ступени CCU с выдержкой на
каждой ступени и затем длительный прогон. Открытые вкладки без действий и
активные пользователи — разные сценарии. Проверить фактический предел SSE,
нагрузку на БД, ошибки, p95/p99 и восстановление после переподключения.

Выход: измеренная ёмкость веба/БД без провайдеров, узкое место и запас до него.
Это не число пользователей, одновременно генерирующих изображения.

### 4. Измерить Kie сквозным потоком

На одном веб-инстансе проверить отдельные image/video сценарии: создание
задания, резерв, отправка через API-ключ, опрос, результат, сохранение файла
и окончательный расчёт кредита. Поднимать темп ступенями; отдельно проверить
короткий всплеск и длительный ровный поток. Фиксировать `429`, ожидание в
очереди, лимиты ключа, неясные исходы и остаток очереди после остановки
нагрузки. `primary` и `secondary` измерять отдельно, не суммируя их без
отдельной проверки. Сессия браузерного кабинета не является измерением
пропускной способности Kie API.

Выход: устойчивые успешные результаты/мин по ключу и типу, стоимость прогона,
время ожидания и необходимый запас очереди.

### 5. Измерить Codex сквозным и длительным потоком

Повторить [план Codex](codex-load-test-plan.md) на выбранном хосте через
публичный веб-путь: авторизация, резерв кредита, отправка, проверка статуса,
PNG/текст и история. Текст и PNG, модели и скорости считать отдельно; затем
проверить согласованную смесь реальных запросов. Поднимать темп ниже
предыдущих проблемных волн, останавливаться при росте `429`, unknown, p95,
очереди или памяти. После ступеней провести длительный прогон и паузу для
проверки освобождения памяти и опустошения очереди. Не переносить
локальные 128/256 напрямую на хостинг.

Выход: устойчивые результаты/мин на один аккаунт и worker, p95, доля отказов,
память за длительное время и проверка аккаунтных ограничений.

### 6. Подготовить и проверить несколько реплик

До теста `2 → 5 → 10` веб-реплик вынести выполнение очередей и восстановление
задач в согласованную модель с единственным владельцем или атомарным захватом;
сделать общий ограничитель отправок Kie на ключ; отделить локальные файлы от
реплик; обеспечить доставку событий между репликами. Для Codex выбрать
маршрутизацию заданий к worker и общий учёт их статусов, чтобы проверка
задания попадала к его исполнителю. Определить судьбу задачи при остановке
реплики и исключить повторную платную отправку. Проверить Telegram polling,
платёжные фоновые задачи и ограничения соединений с БД на нескольких копиях.

Затем повторить веб/Kie/Codex замеры при одинаковом общем трафике на `1`, `2`,
`5`, `10` репликах. Сравнить не только суммарный RPS, но и p95, дубли заданий,
общий предел аккаунтов провайдеров и поведение при выключении одной реплики.
Автомасштабирование включать только после этого этапа.

## Как принять решение о размере системы

Для каждого сценария записать таблицу: конфигурация → устойчивый CCU →
успешных результатов/мин → p95 → ошибки/unknown → CPU/RAM/БД → цена → запас.
Рабочим считать только уровень, выдержавший длительный прогон и всплеск без
потери заданий или нарастающей очереди. Отдельно показать:

1. сколько веб-реплик нужно для целевого CCU без генераций;
2. сколько Kie-ключей/аккаунтов и какой общий темп допустим;
3. сколько Codex worker и какой **общий** темп допускает серверный аккаунт;
4. при каком темпе узким местом становятся БД, файлы, память или провайдер;
5. какую метрику использовать для масштабирования веба, а какую — для
   ограничения приёма генераций и длины очереди.

Если при добавлении реплик общий темп Codex или Kie не растёт, это предел
общего аккаунта/worker либо ошибка координации; дополнительные веб-копии сами
по себе его не устранят.
