# Аккаунты, OAuth и нативные кредиты

Веб-сервис поддерживает отдельные аккаунты с входом Google, VK ID, Яндекс ID, Telegram Login, MAX и по подтверждённому email с паролем. Все способы видны на странице входа; до настройки кнопки неактивны. Первый
успешный вход создаёт пользователя со стартовым пакетом на 150 кредитов. Повторный вход по тому
же `provider + subject` возвращает тот же аккаунт. Email не является ключом
аккаунта; автоматического объединения аккаунтов разных провайдеров нет. Новые способы входа
добавляются адаптерами `authorize/exchange` в `src/auth/providers.js`.

Создание аккаунта и его начальных данных выполняет
`src/services/account-registration.js`: кошелёк, стартовый пакет и основной чат.
OAuth, MAX и email получают операцию `registerAccount` при сборке приложения
в `server.js`. Авторизация сохраняет подтверждённую identity, учётные данные
и сессию; регистрация использует ту же транзакцию. При ошибке весь вход
откатывается, повторный вход не создаёт начальные данные заново.

Общий OAuth-цикл находится в `src/auth/oauth.js`, SQL и правила назначения
аккаунта — в `src/auth/postgres-store.js`. Google выделен в `google.js`;
сборка `google-auth.js` не зависит от PostgreSQL и таблиц продукта.
Инструкция и контракт хранилища: [перенос Google-входа](google-auth-integration.md).

## Подключение

Локальные рабочие запуски команды используют ту же общую PostgreSQL БД, что и
хостинг. `pnpm start` читает `.env` из корня проекта; Docker Compose передаёт
настройки из этого файла через `env_file`. На хостинге настройки передаются
переменными окружения платформы. `.env` передаётся вручную и не входит в Git или
Docker-образ. После его изменения пересоздайте контейнер через
`docker compose up -d --build --force-recreate`; простой restart не обновляет
окружение контейнера.

Автоматической запасной БД нет. Ошибка `DATABASE_VERSION_NEWER` требует
обновления приложения до версии общей схемы, а не перехода на локальную БД.
Создание рабочей локальной БД или смена целевой БД/схемы допускаются только по
явному запросу владельца. Изолированная PostgreSQL тестовых профилей служит
только для тестов и не заменяет проверку рабочего подключения.

1. Подготовьте отдельную PostgreSQL БД для этого приложения. Не используйте
   таблицы или секреты Benz AI. Настройте `DATABASE_URL`, при TLS —
   `DATABASE_SSL=1` с доверенным сертификатом. Проверка сертификата не отключается.
2. В локальном `.env` задайте `MEDIA_AUTH_ENABLED=true` и
   `MEDIA_PUBLIC_ORIGIN=https://ваш-домен` без пути. За reverse proxy передавайте
   исходный Host. Для локальной разработки используйте `http://localhost:3000`.
3. Создайте Google OAuth Web application. Callback:
   `https://ваш-домен/auth/google/callback`. Задайте `GOOGLE_CLIENT_ID` и
   `GOOGLE_CLIENT_SECRET` только на сервере.
4. Создайте VK ID application с callback
   `https://ваш-домен/auth/vk/callback`. Задайте `VK_CLIENT_ID`. Используется
   Authorization Code с PKCE и `device_id`; старый implicit VK OAuth не используется.
   Для Яндекс ID зарегистрируйте приложение с callback
   `https://ваш-домен/auth/yandex/callback` и задайте `YANDEX_CLIENT_ID`,
   `YANDEX_CLIENT_SECRET`. Для Telegram Login добавьте origin и
   `https://ваш-домен/auth/telegram/callback` в разрешённые адреса у @BotFather,
   затем задайте `TELEGRAM_LOGIN_CLIENT_ID`, `TELEGRAM_LOGIN_CLIENT_SECRET`.
   Эти значения отличаются от токена Telegram-бота для уведомлений.
   Для email-входа настройте SMTP: `MEDIA_EMAIL_AUTH_ENABLED=true`,
   `MEDIA_SMTP_HOST`, `MEDIA_SMTP_PORT`, `MEDIA_SMTP_USER`,
   `MEDIA_SMTP_PASSWORD`, `MEDIA_SMTP_FROM`. На порту 465 используется TLS,
   на других портах обязателен STARTTLS. Регистрация активируется после перехода
   по ссылке в письме; ссылка действует 30 минут. Сброс пароля также требует
   письма и завершает все прежние сессии аккаунта. Пароль — от 12 до 128 символов,
   в базе хранится только scrypt-хеш.
   Для MAX нужен бот с мини-приложением на платформе MAX для партнёров.
   Задайте URL мини-приложения `https://ваш-домен/auth/max/confirm`,
   `MAX_LOGIN_BOT_NAME` и `MAX_LOGIN_BOT_TOKEN`. Вход из браузера открывает
   мини-приложение через одноразовый диплинк; сервер проверяет подписанные
   `WebAppData`, включая `start_param`, и возвращает сессию только исходной
   вкладке с HttpOnly-cookie. Токен бота хранится только на сервере.
   Незаполненные или некорректные параметры MAX и SMTP отключают только
   соответствующий способ входа: сервис запускается, а его кнопка остаётся
   видимой и неактивной. Для MAX имя бота задаётся без `@` и содержит
   3–64 латинских буквы, цифры или `_`. Строки-заглушки вместо токена MAX
   не включают вход; при неполной настройке сервер выводит сообщение без токена.
5. Задайте `MEDIA_ADMIN_IDENTITIES=google:subject,vk:subject` для нужных
   идентификаторов разработчика. Узнать свой подтверждённый subject после входа
   можно в `/api/account`, поле `identities`. Перезапустите сервер и войдите снова.
   Первый пользователь не становится администратором автоматически.
6. Запустите `pnpm start`. На старте применится идемпотентная схема из
   `src/database/schema.sql` в транзакции. При ошибке БД сервис не открывает
   анонимный доступ. `MEDIA_SESSION_SECONDS` задаёт срок сессии (по умолчанию 7 дней).

Удаление идентификатора из конфигурации не снимает уже сохранённую роль.
Вкладка «Админ» → «Аккаунты и роли» позволяет назначить user/admin с причиной.
Изменение записывается в журнал и завершает сессии целевого аккаунта; требуется
повторный вход. Последнего администратора понизить нельзя. Явное изменение роли
не отменяется конфигурацией MEDIA_ADMIN_IDENTITIES при следующем входе.
Роль проверяется по БД при каждом запросе, а не доверяется данным браузера.
Серверные решения о роли и отказы в административном доступе собраны в
`src/auth/roles.js`; маршруты APIMart, RouterAI, админ API, файлы админки и
операции над счетами используют это общее правило. Скрытие элементов в
браузере служит только для интерфейса и не выдаёт права.

## Стартер-пак

Новый пользователь автоматически получает 150 кредитов и до первой оплаты имеет
доступ только к GPT-моделям. Ограничение действует на сервере: медиакаталог не
выдаётся аккаунту стартер-пака, а прямой расчёт или запуск медиамодели через API
отклоняется. Старые аккаунты без специальной проводки выдачи пакета не переводятся
в ограниченный режим.

Источник правил — `config/starter-pack.json`, логика —
`src/billing/starter-pack.js`. Модуль фиксирует версию пакета, выдаёт кредиты в
той же транзакции, что и новый аккаунт, сообщает состояние в account API и
показывает агрегаты в разделе «Администрирование» → «Стартер-пак».

Полный каталог открывается только после атомарного зачисления с проводкой
`purchase`. Ручной административный `grant`, остаток баланса и расход стартовых
кредитов не снимают ограничение. `wallet.purchase(accountId, amountUnits,
paymentId, note)` является серверной точкой интеграции будущего подтверждённого
платежа; повтор того же payment ID идемпотентен, а изменённая сумма отклоняется.

Для первоначального назначения по Google email оператор может создать запись
в `media_admin_invitations(email)` в нижнем регистре. Назначение применяется один
раз при входе через Google с `email_verified=true`, после чего сохраняется
consumed_by/consumed_at и событие журнала ролей. Это не публичная регистрация
админов: API создания приглашений нет. Уже существующие аккаунты должны войти
повторно. Email хранится в identity только после подтверждения Google, не
используется для слияния аккаунтов. В схеме v2 добавлены verified_email,
media_admin_invitations и media_role_audit; прежние данные сохранены.

OAuth-адаптеры проверены подставными HTTP-ответами. Живой вход требует регистрации
приложений и настройки callback у соответствующего провайдера. Источники протоколов:
[Google Web OAuth](https://developers.google.com/identity/protocols/oauth2/web-server),
[официальный VK ID SDK](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts),
[Яндекс ID](https://yandex.ru/dev/id/doc/ru/codes/code-url),
[Telegram Login](https://core.telegram.org/bots/telegram-login),
[MAX Mini Apps](https://dev.max.ru/docs/webapps/validation).

## Данные и доступ

PostgreSQL хранит аккаунты, идентификаторы, хеши сессий, одноразовые попытки OAuth,
историю, настройки, черновики, шаблоны, каталог контента, связи с генерациями,
устойчивые задания сохранения, кошельки, резервы и журнал операций. Новые
исходники, результаты Kie и изображения Codex получают отдельный UUID и лежат в
приватном S3 под ключами `accounts/<account-id>/content/<asset-uuid>`; имя,
MIME, размер, SHA-256, владелец и состояние остаются в PostgreSQL. Повтор
сохранения использует тот же UUID, а новая генерация или перегенерация создаёт
новый. Медиа выдаются через `/api/content/<uuid>` после проверки владельца;
endpoint поддерживает byte ranges.

Старые локальные и S3-ссылки остаются читаемыми на переходный период. Команда
`pnpm migrate:content` регистрирует доступные legacy-объекты и отмечает
недоступные как `missing`; `pnpm audit:content` сверяет каталог с S3 без
автоматического удаления. Резервные копии должны охватывать PostgreSQL, S3 и
локальный staging `data/service/`. Сырые OAuth access tokens не сохраняются.

Сессия — случайный непрозрачный токен в HttpOnly/SameSite=Lax cookie, Secure на
HTTPS; в БД хранится SHA-256. OAuth state одноразовый, привязан к cookie браузера
и провайдеру, действует 10 минут; применяется PKCE S256. Cookie сессии заменяется
при входе. API-записи проверяют origin, `X-Media-Client: web` и `X-Media-User`;
последний должен совпадать с текущей сессией и защищает от записи старой вкладки
после смены пользователя. Черновик браузера имеет ключ конкретного аккаунта.

Обычный пользователь получает только свои данные и нативные цены; поля
провайдерской себестоимости, диагностики, внешнего task ID и баланс Kie не
передаются. Администратор открывает `/admin.html`, видит счета и выбирает
аккаунт для просмотра его рабочего пространства с полной диагностикой.
Тестовые начисления требуют суммы, причины и уникального идентификатора;
повтор той же операции безопасен. Это не подтверждённая покупка.

Для пополнения откройте «Администрирование» → «Пополнение кредитов». По умолчанию
выбран свой счёт; можно выбрать пользователя. Укажите сумму с точностью до 0,001
кредита и причину, нажмите «Пополнить». Кнопка «Пополнить мой счёт» возвращает
выбор к администратору. После начисления обновляются доступный баланс и резерв.

Меню по имени/аватару доступно всем: нативный баланс, пополнение, аккаунт,
история, настройки, выход. В аккаунте меняется отображаемое имя, в настройках —
сохранение результатов и параллельность очереди. Администратору доступны вкладка
«Админ» и пункт «Администрирование»; остальным пополнение показывает, что покупки
ещё не подключены. Панель также содержит операции по кошельку, журнал ролей,
«Риски расчётов» и форму ручной сверки задач с неизвестным результатом.

«Риски расчётов» сопоставляют резервы за 7, 30 или 90 дней с проводками,
состоянием задачи и сохранёнными данными поставщика. Положительный расход Kie
или RouterAI при полном возврате клиенту выделяется как критичное расхождение;
возврат после принятия задачи без подтверждённого расхода требует проверки;
неизвестный результат с удержанным резервом показывается отдельно. Экран
показывает первые 200 случаев и их общее число. Данные нашего сервиса сами по
себе не заменяют выписку поставщика: окончательное решение принимается после
сверки по ID задачи в его кабинете.

Администратор оплачивает генерации по тем же нативным тарифам, что и пользователь:
требуются опубликованная цена и достаточный баланс, действуют резерв и списание.
Роль даёт доступ к диагностике и управлению, но не освобождение от оплаты.
Новые генерации в legacy-пространстве запрещены: выберите аккаунт с кошельком.

Старая общая JSON-история не мигрирует и не назначается первому пользователю:
она доступна администратору через `/legacy?account=legacy`. Старые файлы сохраняются.
Windows-приложение остаётся отдельным клиентом; эта авторизация относится к вебу.
В режиме аккаунтов пользователь может привязать личный Telegram через меню
аккаунта в веб-студии. Одноразовая deep link-ссылка действует 10 минут; Telegram
ID связывается не более чем с одним аккаунтом и подтверждается сообщением от
этого ID через Bot API. Генерация из Telegram выполняется в account-scoped
сервисе, проходит те же проверки цены и баланса, резервирует и списывает кредиты
по общему контракту. Стартовый доступ только к GPT не открывает Kie-модели боту.
Telegram можно отвязать из меню аккаунта; отдельный OAuth-вход или регистрация
через Telegram не реализованы. В локальном owner-only режиме без auth бот
сохраняет прежнюю общую очередь.

Для старого локального режима можно явно задать `MEDIA_AUTH_ENABLED=false`,
но только с loopback MEDIA_HOST и без MEDIA_PUBLIC_ORIGIN. Публикация этого
режима через proxy запрещена контрактом. Docker с MEDIA_HOST=0.0.0.0 требует
включённой авторизации.

## Математика кредитов

Временно называем единицу «кредит». Один кредит = 1000 целых минимальных единиц;
денежные операции не используют дробные числа. Модуль `src/billing/pricing.js`
независим от провайдерских `src/costs.js` и `MEDIA_RUB_PER_CREDIT`.

Цены Codex задаются в `config/native-prices.json` либо в проектном файле,
выбранном `MEDIA_PRICING_FILE`. Цены Kie в этот файл не переносятся: сервер
получает актуальный тариф непосредственно из официального прайс-листа Kie при
расчёте и ещё раз перед постановкой платной задачи. По решению владельца от
2026-10-01 опубликованные режимы Codex стоят 10 внутренних кредитов за
запрос, включая GPT-6-Sol и GPT-6-Luna. Неопубликованная модель не может запустить платную генерацию. Пример
формата только для локальных продуктовых цен:

RouterAI использует текущий публичный тариф `GET /api/v1/models`; рублёвая
себестоимость переводится в кредиты общим модулем `src/billing/conversion/`.
Номинал кредита — 1 ₽ цены услуги, а защитный минимум учитывает стоимость
самого выгодного пакета кредитов и удержания. Для посекундных
видеотарифов расчёт идёт по длительности и базовому разрешению модели, которые
явно передаются провайдеру. Цена обновляется перед резервированием. Токенные и
иные варианты без надёжного расчёта до отправки пока заблокированы; прежние
4 кредита для них не применяются. Принятая цена сохраняется в задаче.

```json
{
  "version": "2026-09-example",
  "models": {
    "codex:gpt-5.6-sol:low:standard": { "baseUnits": 10000 },
    "codex:gpt-5.6-sol:low:fast": { "baseUnits": 10000 }
  }
}
```

Формула локальных продуктовых цен первой версии: `baseUnits + duration *
perSecondUnits`. Для Kie применяются единица и вариант из полученной строки
официального тарифа. Если Kie помечает вариант как `with video input`,
посекундная стоимость умножается на сумму длительности входного видео и
результата; длительность сохранённого файла сервер читает сам. После изменения
локальных тарифов перезапустите сервис и увеличьте version. Уже созданные задачи
сохраняют принятую цену и её версию.

- В одной SQL-транзакции создаются задача, резерв и запись журнала. Доступный
  баланс = общий баланс − резерв. Конкурентные операции блокируют строку кошелька.
- `requestId` обязателен для пользовательской отправки. Повтор с тем же содержимым
  возвращает существующую задачу; другое содержимое с тем же ID отклоняется.
- Постановка резервирует принятую цену. Промежуточный `creditsConsumed` от Kie
  не списывает резерв: окончательный расход определяется после `success` или `fail`.
  Положительный итоговый расход списывает принятую цену, явно нулевой освобождает
  резерв, в том числе при `fail`. Для моделей без этого поля списание происходит
  после успешного результата.
  Подтверждённый отказ без расхода, отмена до отправки и ошибка подготовки
  возвращают резерв. Проводка и состояние задачи сохраняются атомарно.
- `unknown` и `unconfirmed` удерживают резерв. Скрытие/очистка очереди его не
  освобождает. Повторные уведомления не создают повторного списания.
- Ручная сверка администратором: POST `/api/admin/reconcile`, JSON
  `{accountId,jobId,outcome,evidence}`, где outcome — `success` или `fail`.
  Требуются та же сессия и заголовки защиты, что у других API-записей. Сохраняются
  администратор и основание; повтор того же решения идемпотентен. Решение следует
  принимать после сверки факта отправки; этот API сам не ищет задачу у провайдера.

Платёжный контур подготовлен, но выключен по умолчанию. `src/payments/` владеет
платежами, адаптером ЮKassa и устойчивыми событиями; `src/commerce/` владеет
карточками, заказами и выдачей кредитов. Включение модуля и новых продаж
разделено флагами `MEDIA_PAYMENTS_ENABLED` и `MEDIA_SALES_ENABLED`.

`config/product-offers.json` содержит пять подготовленных пакетов кредитов.
В веб-клиенте страницы `/app/plans` и `/app/profile` показывают каталог пакетов,
баланс и сведения аккаунта в основном окне в стиле студии. Профиль и тарифы
доступны через меню аккаунта и разделы аккаунта, история кредитов — через
разделы аккаунта. Выбор пакета открывает экран способов оплаты с выбранной
ценой и количеством кредитов. При тестовой заглушке способы недоступны,
заказ и списание не создаются. При активной ЮKassa кнопка ведёт на её страницу
оплаты через сохранённый идемпотентный заказ.
Публичная выдача карточек и checkout остаются выключенными, пока
`MEDIA_PAYMENTS_ENABLED` и `MEDIA_SALES_ENABLED` не включены после настройки
тестового или рабочего магазина.
Продукт передаёт платёжке order ID, точную сумму в копейках и валюту, а после
подтверждения атомарно фиксирует inbox, fulfillment, проводку `purchase` и
состояние заказа. Повтор checkout или события не начисляет кредиты повторно.
Браузерный success redirect только открывает сохранённый заказ.

Адаптер ЮKassa использует серверные shopId/secret, redirect checkout с
`capture=true` и повторно читает объект через API для проверки webhook.
Интеграция проверена на fake и контрактных тестах; реальный тестовый магазин
ещё не подключён. Sandbox должен работать с изолированной продуктовой БД, чтобы
бесплатная тестовая оплата не пополняла общий пользовательский кошелёк.

Архитектура: [платёжный модуль](../tools/project-memory/specs/features/payments-module.md).
Этапы и незавершённые проверки: [план](payments-implementation-plan.md).

`provider-router.js` — граница маршрутизации; сейчас работает только Kie.
Балансировка и автоматический fallback ещё не реализованы. Неоднозначный POST
никогда не повторяется у другого провайдера. Пользовательская цена фиксируется
до выбора/отправки и не выводится из фактической стоимости внешнего запроса.

## Проверки и границы

`pnpm check`, `pnpm test`. Account-тесты запускают реальный SQL PostgreSQL через
PGlite с одним соединением, проверяют OAuth/RBAC, изоляцию, дубли, резервирование,
возвраты и сверку. Это не проверка сетевого PostgreSQL, пула нескольких процессов,
живых OAuth приложений или оплаты. Визуальная проверка веба выполняется вручную.
