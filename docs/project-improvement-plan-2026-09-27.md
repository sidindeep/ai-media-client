# План доработок по аудиту 27 сентября 2026

Основание: [аудит кода, архитектуры и БД](project-audit-2026-09-27.md). Ниже сохранены исходные критерии приёмки; фактическое исполнение указано в конце документа.

## Цель

Сделать публичные сценарии безопасными, денежные операции восстанавливаемыми, БД — согласованной, сборку — воспроизводимой. Сохранить модульный монолит, Vue Composition API и нынешнее пользовательское поведение там, где оно корректно.

Не требуется полное переписывание на ООП, обязательный переход на микросервисы, замена PostgreSQL или внедрение брокера без измеренной необходимости.

## Порядок

### 1. Закрыть границы безопасности — A01, A03

**Тип:** исправления и эксплуатационная настройка.

- Зафиксировать origin executor при проксировании. Отклонять URL с заменой authority, absolute-form и недопустимые варианты разделителей/кодирования.
- Сохранить потоковую передачу загрузок, ограничить upstream timeout, явно фильтровать hop-by-hop и чувствительные заголовки.
- Определить публичные и внутренние маршруты, для которых пересылка допустима; проверять доступ на нужной границе.
- Подготовить отдельную роль миграций и роль runtime с минимальными правами. Смену действующих прав выполнять отдельным проверяемым шагом с возвратом конфигурации при отказе.

**Приёмка:** при включённом auth неавторизованный запрос не достигает посторонней HTTP-заглушки; тестируются обычные маршруты и streamed upload. Runtime не superuser, не создаёт роли/БД, но выполняет все разрешённые сценарии. Миграции работают отдельной ролью.

**Ограничение выпуска:** публичный профиль replicas не включать до устранения A01; широкие права БД устранить до production.

### 2. Исправить сквозные бизнес-сценарии — A02, A04, A05, A06

**Тип:** исправления поведения и регрессионные тесты.

- Преобразовать `client_id` в `clientId` на границе payment repository/контекста.
- Защитить переходы payment блокировкой либо optimistic concurrency; сохранять статус и outbox одной транзакцией.
- Разделить собственную область аккаунта и административный выбор в `accounts.scope`; обновить оба Telegram-вызова.
- Сделать archiveProject атомарным. Проверить create/move/archive/restore чатов при конкуренции и потере соединения.

**Приёмка:**

1. Webhook успешной оплаты подтверждает payment и выдаёт кредиты ровно один раз; повторное событие и перезапуск ничего не удваивают.
2. Одновременные pending/succeeded ответы на двух PostgreSQL-соединениях не возвращают платёж назад из terminal state.
3. Связанный обычный Telegram-пользователь работает со своим аккаунтом; чужой аккаунт запрещён; отвязка прекращает доступ.
4. Ошибка второй записи archiveProject откатывает обе записи; успешный запрос архивирует проект и нужные чаты вместе.

Эти тесты сначала должны воспроизводить найденные ошибки, затем проходить после исправления.

### 3. Довести денежный контур до выбранного объёма продаж — A14

**Тип:** разработка недостающего функционала; отдельный продуктовый контракт.

- Уточнить capabilities: объявлять только реализованные операции, в том числе refunds.
- Подключить durable webhook inbox и восстановление входящих событий, включая раннее событие до фиксации ответа create.
- Реализовать восстановление неизвестного результата внешнего POST без нового произвольного idempotency key.
- Определить обработку просроченного окна идемпотентности, ручную сверку и оповещение о застрявших операциях.
- Выполнить существующий [план платежей](payments-implementation-plan.md) в согласованном объёме; не создавать конкурирующую спецификацию.

**Приёмка:** crash-сценарии до/после внешнего вызова, DB commit и ACK не теряют оплаченный заказ и не дают двойное начисление. Живой sandbox проверяется отдельно от stub. Live-продажи не считать готовыми по одному зелёному unit-набору.

### 4. Укрепить модель БД и миграции — A07, A08, A13

**Тип:** изменения схемы и данных, затем измерение производительности.

- Ввести версионированные неизменяемые миграции, журнал checksum и проверку совместимости версии приложения/БД.
- Сначала сделать read-only preflight: межаккаунтные связи, некорректный JSON, дубли system chats, некорректные даты/состояния.
- Добавить уникальный ключ проекта и составной account/project FK для chats; перед DDL согласовать поведение существующих несовместимых строк, если они найдутся.
- Определить обязательные поля/инварианты по namespace. Для самых важных связей рассмотреть typed columns, сохранив JSONB для provider payloads.
- Проверить, нужен ли уникальный partial index активного system chat, включая archive/restore.
- Измерить запросы chat/project/material counts на реалистичном объёме. Добавлять индексы по результатам EXPLAIN, а не все возможные GIN/expression indexes сразу.
- Рассматривать RLS как отдельную защиту после проектирования tenant context и снятия superuser.

**Приёмка:** чистая установка и upgrade предыдущей версии проходят; несовместимая новая схема не принимается молча; БД отвергает чужой project ID; wallet/reservation инварианты сохраняются. Есть сравнение планов и времени целевых запросов до/после, включая стоимость записи.

**Зависимость:** реальные миграции данных и изменение ролей выполняются только в явно согласованном scope; данный документ не запускает их.

### 5. Сделать проверки и выпуск воспроизводимыми — A09, A10

**Тип:** инфраструктура сборки и тестов.

- Исправить создание временного каталога теста так, чтобы любой тест запускался самостоятельно в чистом контейнере.
- Добавить изолированную настоящую PostgreSQL под test profile текущего Compose для конкурентных денежных/tenant-сценариев. Оставить PGlite для быстрых тестов.
- Включить Vue type-check/build в обязательный pipeline и собирать runtime-фронтенд из текущих исходников.
- Проверять backend-синтаксис по всему исходному набору с учётом формата модулей; подключить умеренный lint для наиболее опасных async/error-patterns.
- Зафиксировать поддерживаемую версию package manager/runtime. Согласовать `engines` с фактическими требованиями сборщика.
- Добавить небольшой браузерный e2e-набор: вход через тестовый auth adapter, черновик, история/пагинация, повторная отправка, ошибки и возврат из checkout.

**Приёмка:** чистый checkout → сборка → контейнерные тесты → health выполняются одной документированной процедурой. Изменение `web/src` гарантированно меняет frontend внутри образа. Все 186 текущих тестов и новые регрессии проходят без предварительно созданных host-каталогов.

### 6. Снизить связность без смены архитектуры — A12, A15

**Тип:** небольшие рефакторинги с сохранением API/поведения.

- Вынести создание сервисов из HTTP в composition root; разделить routes по auth, workspace, generation, content, commerce/admin.
- Описать узкие порты операций: generation submit/read, history page/delta, account access, content read/save. Скрыть прямое использование `accounts.pool`, `service.queue` и `service.history` за нужными командами.
- Разделить studio store по причинам изменения: bootstrap/session, history sync, workspace selection, drafts, generation submission. Composer выделяет upload/quote/validation через composables.
- Договориться о едином runtime-контракте providers; использовать существующий media-фасад только если он действительно упрощает рабочий путь. Иначе явно обозначить его экспериментальным/историческим без обещания универсальности.
- Ввести error codes и схемы на критичных I/O-границах. Типизацию backend развивать через JSDoc/checkJs либо постепенный TypeScript, без массового переписывания ради языка.
- Сводить повторные правила состояний/цен/проекций к общим данным и чистым функциям; не объединять несвязанные use cases только из-за похожего кода.

**Приёмка:** каждый выделенный модуль имеет понятные вход/выход/ошибки, владельца побочных эффектов и тест поведения; существующие публичные сценарии и денежные инварианты сохранены. Уменьшение строк файла само по себе не считается результатом.

### 7. Подтвердить эксплуатацию и привести документацию в порядок — A11, A16, A17

**Тип:** защитные ограничения, эксплуатационные проверки и документация.

- Ограничить скачиваемые результаты по байтам, staging quota и времени; проверить редиректы/адреса и очистку частичных файлов.
- Добавить измеримые сигналы: возраст held/unknown, backlog content/outbox, ошибки сохранения, потеря executor ownership, DB pool wait и доступность providers.
- Зафиксировать RPO/RTO и выполнить восстановление PostgreSQL, S3 и нужного локального состояния в безопасном окружении.
- Описать правила доступа/сроков хранения журналов, включая prompts.
- Синхронизировать README, runbook, technology stack и memory: актуальная схема, Telegram, partial payments, архивный desktop.
- По отдельному решению о возвращении desktop — восстановить исходный предусмотренный каталог, провести IPC sender/navigation review и сборку в единственный `desktop/dist/queue-header`. Архив и пользовательские данные автоматически не удалять.

**Приёмка:** превышение лимита файла корректно останавливается; в staging не остаётся мусор; отказ фонового процесса заметен; восстановленные данные проходят инварианты. Все документированные команды соответствуют доступным файлам.

## Общие правила исполнения

- Работать в текущем проекте, без новой ветки/worktree/альтернативного дистрибутива, если пользователь отдельно их не запросит.
- Сохранять существующие несвязанные изменения. Делить работы на небольшие пакеты с обновлением затронутых контрактов.
- После каждого завершённого пакета файлов: `docker compose up -d --build`, готовность сервисов, `docker compose ps`, `/api/health`; затем релевантные проверки на свежих контейнерах.
- Рефакторинг, исправление поведения, новая функция, миграция данных и эксплуатационная операция должны оставаться явно различимыми работами.
- В этом аудите нет измерения, обосновывающего выделение всего приложения в микросервисы или замену in-process очереди. Такие решения принимать по нагрузке, требованиям доступности и наблюдаемым отказам.
