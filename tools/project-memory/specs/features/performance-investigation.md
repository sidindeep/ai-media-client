## Подтверждённые находки

- В коротком веб-сценарии размер пула БД влияет на задержки: 5 соединений
  при 20 HTTP/с дают p95 полного sync 2,65 с и пропуски; 15 при 40 HTTP/с
  за 180 с дают 0,60 с без пропусков. Штатный default 5 этим исследованием не изменён.
- Исходный SSE ограничивал процесс 20 соединениями. После изменения лимит
  настраивается, а бесплатный прогон открыл 100/100 соединений.
- Исходный всплеск 25 задач Kie double дал p95 принятия POST 9,32 с и
  завершения 18,28 с. После адресных чтений, сокращения SQL и уменьшения
  области блокировки повтор дал p95 POST 1,53 с; последующие 25 холодных/
  тёплых запросов при пуле 15 дали 2,55/1,79 с. Цель ≤1 с не подтверждена.
- История читалась целиком, metadata файлов запрашивались по одному;
  внедрены страницы по 50, пакетное metadata и отдельные активные записи.
- Очередь продолжала пустой tick, а аккаунтные сервисы не выгружались;
  теперь пустая очередь спит и idle сервисы освобождаются через 30 минут.
- Content worker ограниченно параллелен, wait использует паузу 250 мс.
  Worker Codex хранит PNG на диске до подтверждённого сохранения и
  ограничивает число ожидающих задач; 70-минутный mock-тест памяти завершён.
- Исторический Codex 429 подтверждён diagnosis.json; общий обрыв на старом
  RPC timeout уже исправлен. Не выдавать прежнюю гипотезу за текущую причину.

## Границы следующей работы

Выполнение начато: в стенде стабилизированы requestId при replay и пороги
ошибок, добавлена разбивка этапов приёма Kie. В коде сделаны быстрый путь
к существующему основному чату, адресный поиск requestId, ограничение lock
кошелька денежными обновлениями и сон пустой очереди. Результаты повторных
замеров после Docker-пересборки фиксируются отдельно в основном плане.
Последний завершённый бесплатный всплеск: 25/25 success, p95 POST 4,05 с;
100/100 SSE открылись. Платные запросы запрещены владельцем в этом цикле.
Повтор при пуле 15: 25/25 success, p95 POST 1,53 с. Длительный поток
40 HTTP/с за 300 с: 12 005 ответов, 0 ошибок/пропусков, full sync p95
334 мс. На данном DB пул 5 был ограничением; локальная `.env` теперь 15.
Сессии нагрузочного стенда разделены по run-id. Worker Codex сохраняет
PNG на диск и подтверждённо освобождает его после сохранения в media;
70-минутный тест worker завершил 4 095 mock-заданий с PNG и ack; RSS после
прогрева изменился со 100,3 до 104,3 МиБ.
Пустые сервисы аккаунтов теперь освобождаются через 30 минут простоя,
если нет активной очереди или SSE. Для загрузок введён общий бюджет
in-flight 256 МиБ. В `docs/performance-bottlenecks-plan.md` есть таблица
статуса B01–B15; предварительная цель POST ≤1 с ещё не выполнена.
Цели SLO в плане предварительные.
Курсорная пагинация внедрена: `/api/workspace/sync` отдаёт первую страницу и
активные задачи, `/api/workspace/history` — следующие страницы по 50 записей;
тестовая история 10 000 записей прошла 200 страниц без повторов. Потоковая
загрузка 25×16 МиБ и асинхронный ограниченный диагностический журнал проверены
на бесплатном Compose. Веб-реплики могут работать с одним владельцем исполнения
по [контракту](../../../../docs/replica-ownership.md): все записи пересылаются
executor, события приходят через PostgreSQL LISTEN/NOTIFY, второй executor
отсекается session advisory lock. Многовладельческое распределённое исполнение
не входит в этот режим.

Чистый 30-минутный прогон одной web-реплики с пулом 15 при 8 циклах/с
(40 HTTP/с) завершил 14 400/14 400 циклов и 72 000 HTTP без ошибок и
пропусков; p95/p99 полного sync 265/283 мс. После исходной перегрузки
обнаружены оставшиеся после прерывания терминала контейнеры k6; их
остановили перед чистым прогоном. Сырые отчёты лежат в игнорируемых
`artifacts/load-tests/mixed30replica2_20260926/` и
`artifacts/load-tests/memory-codex-20260926.json`.

Десятиминутная пауза после веб-прогона оставила health доступным и очередь
пула пустой, но RSS web удержался на 223,6 МиБ вместо возврата к исходному
уровню. На свежем стенде 2 web-копии с пулом 5 при 8 циклах/с завершили
408/480 циклов (72 пропуска, p95 полного sync 1,90 с); 5 и 10 копий
завершили 480/480 без пропусков (p95 307 и 303 мс). После остановки executor
web сохранил чтение 200 и вернул 503 на запись; после рестарта mock-задача
имела одну отправку, один резерв, одно списание и `held=0`. Короткие ступени
не доказывают долговременную ёмкость 5/10, а единичный executor остаётся
общим пределом записей и платных отправок.

Сохранить изоляцию аккаунтов, атомарность денег, уникальность requestId,
безопасный unknown, актуальную цену перед отправкой, курсор UI, доступность
файла и проверку его целостности. Несколько реплик требуют общей координации;
простое снятие service.lock её не заменяет. Платный бюджет не задан.

Повтор 2026-09-26 подтвердил медленный POST при всплеске. Начальное принятие
Kie-задачи теперь записывает резерв, ledger, историю и событие журнала одной
атомарной SQL-операцией. Промежуточные состояния не держат блокировку кошелька;
восстановление пустой очереди не делает второе чтение. На выделенном mock-стенде
25 запросов одного аккаунта ускорились с p95 10,8 до 1,34 с, все проводки
сошлись. 25 разных аккаунтов через web дали p95 1,63–1,75 с после исправления
вместо 2,83 с в повторном базовом прогоне. Пул 30 вместо 15 ухудшил холодный
p95 до 6,22 с из-за открытия удалённых соединений, поэтому настройку пула не
увеличивать. Цель ≤1 с на этой удалённой БД остаётся непроверенной; не выдавать
улучшение кода за выполнение этой цели.
Контрольный повтор финального кода на 25 разных аккаунтах через web дал p95
POST 1,94 с и 25/25 success без расхождений ledger; вариативность удалённой
БД сохраняется. Пользователь одобрил Git push отладочной версии 0.3.11 с этим
известным ограничением; это не подтверждение SLO ≤1 с.
